 `final` 除了“不可变”，还可以从 JVM 内存模型、性能优化（JIT 内联）、安全发布、设计模式 等层面展开。


## 一、三大核心作用（基础层）

| 修饰目标 | 作用 | 典型场景 |
| :---: | :--- | :--- |
| 类 | 不能被继承 | String、Integer 等包装类、工具类 |
| 方法 | 不能被重写（override） | 模板方法模式中防止子类篡改核心步骤 |
| 变量 | 基本类型：值不可变；引用类型：引用地址不可变（对象内部状态仍可变） | 常量定义、不可变对象（配合 immutable） |

### 1.1 修饰类 —— 断子绝孙
```java
public final class String {  // JDK 核心类
    // 不可被继承，保证安全性（防止子类篡改字符串常量池行为）
}
```
### 1.2 修饰方法 —— 锁定行为
```java
public class Parent {
    public final void init() {  // 模板方法，子类不允许改变启动流程
        loadConfig();
        doInit();
    }
}
```

### 1.3 修饰变量 —— 分两类

| 类型 | 含义 | 示例 |
| :---: | :--- | :--- |
| 基本类型 | 数值本身不可变 | final int MAX = 100; |
| 引用类型 | 指针地址不可变，但指向的对象内容可变 | final List<String> list = new ArrayList<>(); 可 add/remove，但不能 list = new ArrayList<>() |
```java
final List<String> list = new ArrayList<>();
list.add("hello");      // 允许（对象状态变了）
list = new ArrayList<>(); // 编译错误（引用地址变了）
```

## 二、final 与不可变性（进阶）

面试高频陷阱：final ≠ 不可变（Immutable）

> 引用不可变 ≠ 对象不可变。

要实现真正的不可变类（如 String），需要同时满足：
1. 类声明为 final（防止子类破坏不可变性）
2. 所有字段 private final
3. 不提供 setter
4. 若字段是可变引用（如 Date、List），返回防御性拷贝（new ArrayList<>(inner)）
```java
public final class ImmutablePerson {
    private final String name;
    private final List<String> hobbies;

    public ImmutablePerson(String name, List<String> hobbies) {
        this.name = name;
        this.hobbies = new ArrayList<>(hobbies); // 防御性拷贝
    }

    public List<String> getHobbies() {
        return new ArrayList<>(hobbies); // 返回拷贝，不暴露内部引用
    }
}
```

## 三、JVM 底层与性能优化（加分层）

### 3.1 JIT 内联优化（Inlining）

final 方法在编译期（或 JIT 运行时）可以被直接内联展开，省去虚方法表（vtable）查找，减少方法调用的栈帧开销。
```java
public final int compute() { return 100; }
```
// JIT 可能将调用处直接替换为常量 100，而不是生成 CALL 指令

> 在极端高频调用的场景（如支付金额计算、风控规则匹配），final 的微秒级优化在 QPS 1000+ 系统中会有可观测的 RT 降低。

### 3.2 安全发布（Safe Publication）

JMM（Java 内存模型）保证：当构造函数中对象的 final 字段赋值完成后，其他线程一定能看到该字段的正确初始值，无需额外的 volatile 或 synchronized。

> 这是实现线程安全不可变对象的底层基石。例如 String 的 hashCode 延迟初始化虽然是非 final，但通过 volatile 配合做了双检锁，而真正的不可变对象直接用 final 字段即可保证所有线程可见一致性。


## 四、final 在匿名内部类 / Lambda 中的特殊规则

在匿名内部类或 Lambda 表达式中，只能访问外部的 final 或 effectively final（实际未变但未声明）的局部变量。
```java
public void test() {
    String prefix = "user_"; // 实际未变 => effectively final
    Runnable r = () -> System.out.println(prefix + "123");

    // String prefix = "admin_"; //  若取消注释则报错，因为 prefix 被改变了
}
```

原理：Java 编译器会将局部变量拷贝到匿名类的字节码中作为实例变量。为了防止数据不一致（外层修改 vs 副本不同步），强制要求变量不可变。


## 五、 final 关键字的作用

final 有三层作用：
1. 语法层面：修饰类不可继承、方法不可重写、变量引用不可变。
2. 并发层面：final 字段在 JMM 中有安全发布保证，对象构造完成后所有线程看到的 final 字段值是一致的，这是实现不可变对象（如 String、LocalDateTime）的基础。
3. 性能层面：final 方法有助于 JIT 编译器做内联优化，省去虚表查找，在支付中台这种高并发（QPS 1000+）场景中，大量工具方法和核心判读逻辑加 final，对整体 RT 有积极影响。

不过要注意，final 修饰引用类型时只保证指针不变，对象内容依然可变，所以构建纯不可变对象还需要做防御性拷贝。


## 六、高频易错点总结

| 误区 | 纠正 |
| :--- | :--- |
| final 对象完全不可变 | 引用不可变，对象内部状态可变 |
| 所有变量都要加 final | 只有常量、配置类、跨线程共享的不可变对象才加，滥用会增加代码冗余 |
| final 方法比非 final 快 | 是的，JIT 会倾向于内联，但在热方法上才明显，非极端情况可忽略 |
| final 类中的方法自动 final | 是的，final 类中的所有方法隐式 final |


## 七、结合项目

- 常量类：BizConstants.REDIS_KEY_PREFIX、EXPIRE_TIME 等配置常量。
- DTO 构造器参数：防止请求参数在构造后被篡改（配合 @RequestBody 中的 final 字段）。
- 工具类的静态方法：声明为 final，防止子类覆盖破坏逻辑（如 DateUtils.format()）。
- 核心模板方法：对账处理器模板类中的 execute() 方法加 final，确保流程不被子类破坏，保持业务一致性。
