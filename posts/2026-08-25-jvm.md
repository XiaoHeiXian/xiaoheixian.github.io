> JVM 内存分为 **线程私有**（程序计数器、虚拟机栈、本地方法栈）和 **线程共享**（堆、方法区）两大部分。在项目中，**堆** 是 GC 主要关注区，**栈** 决定线程数量，**方法区** 存类元信息。


## 核心结论

| 区域 | 线程归属 | 存什么 | 项目关联 |
| :---: | :---: | :--- | :--- |
| **程序计数器** | 私有 | 当前执行字节码的行号指示器 | 几乎不用关心，JVM 自己管 |
| **虚拟机栈** | 私有 | 方法调用栈帧（局部变量、操作数栈、方法出口） | **栈深度不足 = StackOverflowError**；每个线程独立分配内存 |
| **本地方法栈** | 私有 | native 方法调用 | 基本不涉及，JVM 内部使用 |
| **堆** | 共享 | 所有对象实例、数组 | **GC 重灾区**：支付订单对象、缓存对象，分代回收核心区 |
| **方法区（元空间）** | 共享 | 类信息、常量、静态变量、JIT 编译后的代码 | **类加载膨胀 + 常量池溢出** 可能导致 OOM |


## 一、各区域详解

### 1.1 程序计数器（Program Counter Register）

- **线程私有**，记录当前线程执行的字节码行号。
- 分支、循环、跳转、异常处理、线程恢复都依赖它。
- **唯一一个不会 OOM 的区域**。

### 1.2 虚拟机栈（Java Virtual Machine Stack）

- **线程私有**，每个方法执行时创建一个 **栈帧（Stack Frame）**。
- 栈帧包含：**局部变量表**、**操作数栈**、**动态连接**、**方法出口**。
- 方法调用 = 入栈，方法结束 = 出栈。
- **两种异常**：
  - 线程请求栈深度 > JVM 允许深度 → `StackOverflowError`
  - 栈动态扩展时内存不足 → `OutOfMemoryError`

**项目关联：** 支付中台高峰期 QPS 1000+，每个请求至少 2-3 层方法调用链（Controller → Service → Mapper），若每层都创建大量对象，栈内存压力大。通过 **减少不必要的方法嵌套**、**避免递归** 来控制栈深度。

### 1.3 本地方法栈（Native Method Stack）

- **线程私有**，为 `native` 方法服务（如 `Object.hashCode()`、`Unsafe` 相关操作）。
- HotSpot 虚拟机将本地方法栈和虚拟机栈合二为一。

### 1.4 堆（Heap）

- **线程共享**，所有对象实例和数组都在堆上分配，是 **GC 管理的主要区域**。
- 物理上不连续，逻辑上连续，大小通过 `-Xms` 和 `-Xmx` 控制。
- 分代回收（年轻代 + 老年代）是主流回收策略，但 G1、ZGC 已不再严格分代。

```java
// 堆上分配对象示例
Order order = new Order();  // Order 对象在堆上，引用 order 在栈上
```

**项目关联：**
- 支付中台日订单 50 万，每个订单对象（含金额、状态、商户号等字段）约占用 200-300 字节。**50 万订单对象 = 约 100-150 MB 堆内存**，加上缓存、上下文对象，高峰期堆内存使用约 4-6 GB。
- **实践配置**：生产环境 `-Xms8g -Xmx8g`（减少扩容抖动），使用 G1 垃圾回收器（`-XX:+UseG1GC`）。
- **监控**：通过 Grafana + Prometheus 监控堆内存使用率，超过 80% 触发扩容告警。平稳期堆内存稳定在 4-5 GB，GC 频率控制在 1 次/分钟以内，单次 GC 耗时 < 50ms。
- **大对象（如批量导出的 Excel）直接进入老年代**，配合 `-XX:PretenureSizeThreshold` 控制，避免频繁 YGC 搬运。

### 1.5 方法区 / 元空间（Method Area / Metaspace）

- **线程共享**，存储 **类信息**、**常量池**（字面量 + 符号引用）、**静态变量**、**JIT 编译后的代码**。
- JDK 1.8 后将方法区从永久代（PermGen）改为 **元空间（Metaspace）**，使用本地内存，默认无上限。

**项目关联：**
- 支付中台拆分为 9 个微服务，每个服务启动时加载的类数量约 5000-8000 个（Spring Boot 自动配置 + 业务类）。
- **配置**：`-XX:MaxMetaspaceSize=512m`，防止类加载过多导致内存膨胀。
- **Sharding-JDBC + 枚举类** 场景要特别注意：每个分表映射的 Mapper 类都会被加载，若枚举类膨胀 + 分表数量多（16库 × 12月 = 192张表），元空间压力会明显上升。建议配合 **类卸载**（`-XX:+CMSClassUnloadingEnabled`）及时回收。


## 二、JVM 内存参数调优（项目实战）

在**支付中台**项目中，我们针对 JVM 做了如下配置和调优：

### 2.1 核心 JVM 启动参数

```text
-Xms8g -Xmx8g
-XX:+UseG1GC
-XX:MaxGCPauseMillis=50
-XX:G1HeapRegionSize=16m
-XX:+PrintGCDetails -Xloggc:/var/log/gc.log
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/var/dump/
```

**每项含义：**

| 参数 | 含义 | 项目为什么这么配 |
| :--- | :--- | :--- |
| `-Xms8g -Xmx8g` | 初始堆 = 最大堆 = 8GB | 避免扩容抖动（Elastic Scaling）影响 RT，支付交易对延迟敏感 |
| `-XX:+UseG1GC` | 使用 G1 回收器 | 替代 CMS，可预测停顿时间，适合大堆内存（>4GB）场景 |
| `-XX:MaxGCPauseMillis=50` | 目标 GC 停顿 ≤ 50ms | 支付接口 P99 要求 < 200ms，GC 停顿不能拖后腿 |
| `-XX:G1HeapRegionSize=16m` | G1 分区大小为 16MB | 堆 8GB / 16MB = 512 个 Region，平衡回收粒度 |
| `-XX:+HeapDumpOnOOMError` | OOM 时自动 dump 堆快照 | 出问题能快速定位是内存泄漏还是流量冲击 |

### 2.2 发散

**G1 回收和 CMS 有什么区别？为什么选 G1？**

CMS 注重低停顿，但容易产生内存碎片，且 Full GC 时是单线程的，大堆场景下停顿不可控。G1 将堆划分成多个相等 Region，通过预测模型控制停顿时间，回收时优先回收垃圾最多的 Region（Garbage First），适合大堆内存场景。支付中台堆内存 8GB，用 G1 比 CMS 更稳，**Full GC 次数从每月 2-3 次降至 0**。

**怎么处理 OOM？**

缴费项目开学季高峰期，**堆内存飙到 7.2GB，触发 OOM**。排查发现是 **缓存预热方案** 有缺陷：几百所学校的层级树一次性加载到堆内存，且没有设置软引用淘汰。

优化方案：
1. 调整 `-Xmx` 从 4GB → 8GB
2. 缓存策略从 **「全部加载」改为「按需加载 + Caffeine 过期淘汰」**
3. 层级树对象改为 **弱引用（WeakReference）** 缓存，内存不足时可被回收
4. 增加 Redis 存储层级树 JSON，作为二级缓存兜底


## 三、总结

JVM 内存从线程归属上分为两类，**线程私有的**和**线程共享的**。

线程私有的有三个：**程序计数器**、**虚拟机栈**、**本地方法栈**。程序计数器是当前线程执行字节码的行号指示器，是唯一不会 OOM 的区域。虚拟机栈每个方法执行时创建一个栈帧，存放局部变量、操作数栈和方法出口，递归太深会 StackOverflowError，创建太多线程会 OOM。本地方法栈是给 native 方法用的，HotSpot 里和虚拟机栈合在一起。

线程共享的有两个：**堆** 和 **方法区（元空间）**。堆是所有对象和数组分配的地方，也是 GC 最关注的地方。我们支付中台项目用 G1 回收器，堆配了 8GB，日订单 50 万，GC 停顿控制在 50ms 以内。方法区存类信息、常量池和静态变量，JDK 1.8 后改成元空间，用本地内存。我们每个微服务加载的类大概 5000-8000 个，元空间配了 512MB。

实际项目里，我们还做了几件事：OOM 自动 dump 堆快照；通过 Grafana 监控堆内存和老年代占用；G1 的 MaxGCPauseMillis 根据实际压测结果从 100ms 调到了 50ms。


## 四、再深一层：JVM 内存模型（Java Memory Model，JMM）的区分

> "JVM 内存模型"，可能不止"运行时数据区"，也可能是 **JMM（Java 内存模型）**。

**JVM 内存模型（运行时数据区）** 指的是物理上内存如何划分（堆、栈、方法区等），是 **存储层面的东西**。

**JMM（Java 内存模型）** 指的是 Java 语言层面定义的一套 **多线程并发访问的规范**，涉及 `volatile`、`synchronized`、`happens-before` 原则、主内存与工作内存的交互等。它的核心是 **保证并发环境下的可见性、有序性和原子性**。

**快速区分：**

| 概念 | 关注点 | 发散 |
| :--- | :--- | :--- |
| JVM 内存模型（运行时数据区） | 内存怎么划分、存什么 | "堆和栈的区别？""GC 怎么回收？" |
| JMM（Java 内存模型） | 并发访问规范、可见性/有序性 | "volatile 的可见性如何保证？""happens-before 原则有哪些？" |


## 五、堆和栈的区别（高频附加题）

**堆和栈的区别**

| 维度 | 栈（虚拟机栈） | 堆 |
| :--- | :--- | :--- |
| 线程归属 | 私有 | 共享 |
| 存什么 | 局部变量、操作数栈、方法出口 | 所有对象实例、数组 |
| 生命周期 | 跟随线程，方法结束即释放 | 跟随 GC，对象不再引用时回收 |
| 内存大小 | 较小（默认 1MB） | 较大（GB 级别） |
| 异常 | StackOverflowError / OOM | OOM（内存泄漏/内存溢出） |
| 性能 | 分配释放极快（入栈出栈） | 分配慢（需要 GC 介入） |
| 可见性 | 线程隔离，不存在可见性问题 | 线程共享，需要考虑可见性 |

> **结合项目一句话：** 在支付中台，我们追求低延迟，所以尽量把 **轻量级临时变量**（如方法内的订单 ID、金额计算中间值）放在栈上，避免频繁堆分配触发 YGC。同时通过 **对象池**（如连接池、线程池）复用大对象，减少堆上对象的创建和回收压力。


## 六、内存溢出（OOM）场景与排查

**遇到过的 OOM 和排查方法**

### 场景一：堆内存溢出（Heap OOM）

**现象**：开学季高峰期，缴费管理页导出报表时频繁超时，最终服务崩溃，日志报 `java.lang.OutOfMemoryError: Java heap space`。

**排查过程：**
1. 检查 `-Xmx` 配置 → 发现只有 4GB，但堆内存使用率达到 95%
2. 导出 dump 文件（`jmap -dump:format=b,file=heap.hprof <pid>`）
3. 用 MAT（Memory Analyzer Tool）分析 → 发现 `HashMap` 中缓存了 18 万+ 的缴费记录对象，未被回收
4. 定位代码：导出报表时，先把所有数据查出来放到内存中再写入 Excel

**解决方案：**
1. 导出改为 **分批查询 + SXSSFWorkbook（只保留 100 行在内存）**
2. 缓存从 HashMap 改为 Caffeine（设置 `maximumSize` 和 `expireAfterWrite`）
3. 堆内存从 4GB 扩到 8GB，G1 停顿目标从 100ms 降到 50ms

### 场景二：元空间溢出（Metaspace OOM）

**现象**：支付中台交易服务连续运行 3 周后，突然 OOM 崩溃，日志报 `java.lang.OutOfMemoryError: Metaspace`。

**排查过程：**
1. `jstat -gc <pid>` 观察 Metaspace 使用量 → 发现持续缓慢增长，从未下降
2. 检查启动参数 → 没有设置 `-XX:MaxMetaspaceSize`，默认使用本地内存无上限
3. 用 `jcmd <pid> GC.class_stats` 分析 → 发现 Sharding-JDBC 为每月分表动态生成的 Mapper 类没有被卸载

**解决方案：**
1. 增加 `-XX:MaxMetaspaceSize=512m`，设置上限防止无限膨胀
2. 开启类卸载：`-XX:+CMSClassUnloadingEnabled`
3. 升级 Sharding-JDBC 版本，利用其内置的元数据缓存机制减少重复类加载
4. 增加监控告警：Metaspace 使用率超过 80% 时触发告警
