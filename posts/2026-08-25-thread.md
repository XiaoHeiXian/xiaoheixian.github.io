> 线程池的核心参数一共有 7 个，分别是 `corePoolSize`（核心线程数）、`maximumPoolSize`（最大线程数）、`keepAliveTime`（空闲存活时间）、`TimeUnit`（时间单位）、`BlockingQueue`（阻塞队列）、`ThreadFactory`（线程工厂）、`RejectedExecutionHandler`（拒绝策略）。其中决定线程池行为的是 **前三个 + 队列** 的配合关系。在支付中台项目中，我们针对 **IO 密集型**（业务处理）和 **CPU 密集型**（加密验签）场景分别做了不同配置。


## 核心结论

线程池执行任务的核心逻辑：

> **核心线程数满了 → 任务进队列 → 队列满了 → 创建临时线程到最大线程数 → 最大线程也满了 → 执行拒绝策略。**


## 一、七个核心参数详解

### 参数1：corePoolSize（核心线程数）

- **含义**：线程池中**一直存活**的线程数量，即使它们处于空闲状态也不会被回收（除非设置了 `allowCoreThreadTimeOut`）。
- **什么时候创建**：默认情况下，任务来了才创建（懒加载）；也可以通过 `prestartCoreThread()` 提前预热。
- **项目关联**：支付中台启动时，通过 `prestartAllCoreThreads()` 预热核心线程，避免第一个请求慢。

### 参数2：maximumPoolSize（最大线程数）

- **含义**：线程池中**允许存在的最大线程数量**，包含核心线程 + 临时线程。
- **什么时候创建临时线程**：**核心线程满了 + 队列也满了**，才会创建新线程直到达到 maximumPoolSize。
- **注意**：如果队列是无界的（如 `LinkedBlockingQueue`），maximumPoolSize 参数基本无效，因为队列永远不会满。

### 参数3：keepAliveTime + 参数4：TimeUnit（空闲超时时间）

- **含义**：**临时线程**（超出 corePoolSize 的那部分）空闲多久后被回收。
- **TimeUnit**：时间单位（秒、毫秒、分钟等）。
- **项目关联**：支付中台交易服务，`keepAliveTime` 设为 60 秒。高峰过后临时线程快速回收，释放系统资源。

### 参数5：BlockingQueue（阻塞队列）

- **含义**：存放**等待执行**的任务的队列。
- **决定了线程池的行为模式**。

### 参数6：ThreadFactory（线程工厂）

- **含义**：用于创建线程的工厂，可以自定义线程名称、优先级、是否守护线程。
- **项目关联**：统一命名规则 `trade-pool-%d`，便于排查问题（`jstack` 时一眼看出是哪个线程池的线程）。

### 参数7：RejectedExecutionHandler（拒绝策略）

- **含义**：当 **线程池已关闭** 或 **核心线程满 + 队列满 + 最大线程满** 时，对新提交的任务执行的处理策略。


## 二、任务提交的完整流程

当调用 `execute(task)` 时，按以下顺序处理：

**第1步（核心线程检查）**
当前线程数 < corePoolSize？
→ 是：新建核心线程执行任务
→ 否：进入第2步

**第2步（队列检查）**
队列.offer(task) 是否成功？
→ 是：任务进入队列等待
→ 否（队列满了）：进入第3步

**第3步（最大线程检查）**
当前线程数 < maximumPoolSize？
→ 是：新建临时线程执行任务
→ 否：进入第4步

**第4步（拒绝策略）**
执行 `RejectedExecutionHandler.rejectedExecution(command, executor)`


## 三、阻塞队列选型（高频考点）

| 队列类型 | 特点 | 适用场景 | 风险 |
| :--- | :--- | :--- | :--- |
| **ArrayBlockingQueue**（有界） | 数组结构，有界，FIFO | 线程数可控，任务量明确 | 队列满了触发拒绝策略，需合理设置 |
| **LinkedBlockingQueue**（有界/无界） | 链表结构，默认 **Integer.MAX_VALUE**（无界） | Executors.newFixedThreadPool 默认用它 | **无界队列可能堆积海量任务导致 OOM** |
| **SynchronousQueue**（无存储） | 不存任务，直接交给线程执行 | Executors.newCachedThreadPool 默认用它 | 线程数可能暴涨，需配合大 maximumPoolSize |
| **PriorityBlockingQueue**（优先级） | 支持任务优先级排序 | 需要任务插队场景 | 无界，同样有 OOM 风险 |

> 我们在支付中台用的 **ArrayBlockingQueue 有界队列 + 合理拒绝策略**，不用无界队列，防止突发流量把内存打爆。


## 四、四种拒绝策略（RejectedExecutionHandler）

JDK 内置了 4 种策略：

| 策略 | 行为 | 适用场景 | 风险 |
| :--- | :--- | :--- | :--- |
| **AbortPolicy（默认）** | 直接抛出 `RejectedExecutionException` | 重要任务，不能丢，必须感知到失败 | 调用方需要 try-catch 处理异常 |
| **CallerRunsPolicy** | 交给**调用方线程**（提交任务的线程）同步执行 | 不能丢任务，且希望降低提交速度（反馈机制） | 调用方线程被阻塞，可能拖垮上游 |
| **DiscardPolicy** | 静默丢弃，**不抛异常** | 非核心业务，丢几笔无所谓 | 无感知，需配合监控 |
| **DiscardOldestPolicy** | 丢弃**队列中最早等待**的任务，然后重新提交当前任务 | 追求最新数据，旧数据无意义（如实时日志） | 可能导致重要旧任务丢失 |

> **项目关联：** 支付中台交易核心链路用 **AbortPolicy + 自定义告警**，拒绝时打印日志 + 钉钉报警，人工介入处理。非核心日志上报用 **DiscardPolicy**，丢了不心疼，不影响主流程。


## 五、项目实战：支付中台的线程池配置

在支付中台和口袋易缴项目中，我们根据业务场景做了不同配置：

### 场景一：交易核心链路（IO 密集型）

业务特点是 **大量数据库查询、外部接口调用（支付通道、风控）**，CPU 计算少，线程可以多配。

corePoolSize = CPU核心数 * 2
maximumPoolSize = CPU核心数 * 4
keepAliveTime = 60秒
队列 = ArrayBlockingQueue(2000)
拒绝策略 = AbortPolicy + 钉钉告警

### 场景二：对账清算任务（CPU 密集型）

业务特点是 **大量金额计算、对账比对、数据聚合**，CPU 计算密集，线程数不宜过多（上下文切换开销大）。

corePoolSize = CPU核心数 + 1
maximumPoolSize = CPU核心数 * 2
keepAliveTime = 30秒
队列 = ArrayBlockingQueue(1000)
拒绝策略 = CallerRunsPolicy（生产消费同步，反压上游）

### 场景三：异步通知推送（高吞吐、允许延迟）

业务特点是 **支付回调通知商户、短信/钉钉推送**，量大但实时性要求不高。

corePoolSize = 5
maximumPoolSize = 20
keepAliveTime = 60秒
队列 = LinkedBlockingQueue(10000)（有界，防止堆积）
拒绝策略 = DiscardPolicy + 记录日志 + 补偿任务兜底

### 实际代码配置：

```java
// 交易核心线程池配置示例
@Bean(name = "tradeExecutor")
public ThreadPoolExecutor tradeExecutor() {
    int cpuCores = Runtime.getRuntime().availableProcessors();
    return new ThreadPoolExecutor(
        cpuCores * 2,           // corePoolSize
        cpuCores * 4,           // maximumPoolSize
        60L,                    // keepAliveTime
        TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(2000),
        new CustomThreadFactory("trade-pool"),
        new RejectedExecutionHandler() {
            @Override
            public void rejectedExecution(Runnable r, ThreadPoolExecutor executor) {
                // 钉钉告警 + 打印日志
                alarmService.send("交易线程池已满，拒绝任务");
                throw new RejectedExecutionException("交易线程池队列满");
            }
        }
    );
}
```

## 六、总结

> 线程池的核心参数

线程池核心参数有 7 个，前 5 个最重要的：

第一个是 `corePoolSize`，核心线程数，这些线程会一直存活，即使空闲也不回收。第二个是 `maximumPoolSize`，最大线程数，包含核心线程和临时线程。第三个和第四个是 `keepAliveTime` 和 TimeUnit，控制临时线程空闲多久被回收。第五个是 `BlockingQueue`，阻塞队列，存放等待执行的任务。

这里有一个很重要的执行顺序是：**核心线程满 → 进队列 → 队列满 → 创建临时线程 → 最大线程满 → 拒绝策略**。

第六个是 ThreadFactory，用来给线程起名字，方便排查问题。第七个是拒绝策略，JDK 提供 4 种：AbortPolicy（抛异常）、CallerRunsPolicy（调用者线程执行）、DiscardPolicy（静默丢弃）、DiscardOldestPolicy（丢弃最老任务）。

在我们支付中台项目里，核心交易链路用的是有界队列，配合 AbortPolicy 加钉钉告警。因为支付业务不能丢任务，队列满了说明下游已经扛不住了，与其继续堆任务导致 OOM，不如直接拒绝让上层感知到问题。我们还根据业务做了区分，IO 密集型配 CPU 核心数 2 倍的线程数，CPU 密集型（比如对账清算）配 CPU 核心数 + 1 个。

> `corePoolSize` 和 `maximumPoolSize` 的区别

核心线程创建后常驻，不会被回收；临时线程只有在队列满了之后才会创建，空闲超过 keepAliveTime 就会被回收。需要注意，如果用的是无界队列（比如默认的 LinkedBlockingQueue），maximumPoolSize 参数就形同虚设了，因为队列永远不会满，永远不会创建临时线程。


## 七、高频易错点总结

| 误区 | 纠正 |
| :--- | :--- |
| 核心线程满了立刻创建临时线程 | **错**：先入队列，队列满了才创建临时线程 |
| `corePoolSize` = 0 也可以 | **可以**，但会导致任务全走队列，如果队列无界且任务持续涌入，内存会爆 |
| `Executors.newFixedThreadPool` 很安全 | 它用的是无界队列，可能导致 OOM，**阿里规约明确禁止用 Executors 工厂方法** |
| `Executors.newCachedThreadPool` 很高效 | 它的 maximumPoolSize = Integer.MAX_VALUE，任务量大时线程数无限膨胀，**同样存在风险** |
| 拒绝策略只有 4 种 | 除了 4 个内置策略，还可以**自定义**拒绝策略（比如做降级、落库补偿） |


## 八、阿里规约引申

在项目中不用 Executors 工具类，因为Executors 工厂方法存在隐患：
1. `newFixedThreadPool` 和 `newSingleThreadExecutor` 用的是无界 LinkedBlockingQueue，任务堆积可能导致 OOM。
2. `newCachedThreadPool` 和 `newScheduledThreadPool` 的最大线程数是 Integer.MAX_VALUE，可能创建过多线程，耗尽操作系统资源。

所以我们在项目中 **强制使用 ThreadPoolExecutor 自定义参数**，根据业务场景配置有界队列和合理拒绝策略。这一点也符合《阿里巴巴 Java 开发手册》的规约。
