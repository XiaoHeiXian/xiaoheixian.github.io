## 一句话概括

Jar 包冲突本质是 **依赖传递导致的类路径污染**。核心解决思路分两步：**Maven Dependency Tree 定位冲突 → exclusions 排除 + 父 POM 锁版**，遇到无法排除的硬编码 SPI 加载时用 **Shade 插件重命名隔离**。`NoSuchMethodError` / `NoClassDefFoundError` 大概率是 Jar 包冲突导致。


## 核心流程（两步走）

### 第一步：定位冲突（找到肇事者）

**1.1 依赖树分析**

    mvn dependency:tree -Dverbose

重点关注：
- 同一 artifactId 出现多个不同版本。
- Maven 仲裁机制（默认策略）：
  - **最短路径优先**：路径最短的版本胜出。
  - **最先声明优先**：路径相同时，先声明的胜出。
- 注意：Maven 选的版本**不一定是业务想要的版本**。

**1.2 运行时类加载确认（锁定“真凶”）**

方式一：启动参数打印类加载日志

    -XX:+TraceClassLoading
    或
    -verbose:class

可查看 JVM 实际从哪个 Jar 包加载了报错的类。

方式二：Arthas 在线诊断（生产环境推荐，无需重启）

    sc -d ClassName        # 查看类加载器信息
    jad ClassName          # 反编译确认方法签名

方式三：编程式确认（写几行测试代码）

    Class.forName("xxx.ClassName").getProtectionDomain().getCodeSource().getLocation()


### 第二步：解决冲突（对症下药）

**2.1 精准排除（第一选择）**

在 `pom.xml` 中用 `<exclusions>` 剔除传递性依赖里的老版本：

    <dependency>
        <groupId>com.alipay</groupId>
        <artifactId>alipay-sdk</artifactId>
        <version>3.7.0</version>
        <exclusions>
            <exclusion>
                <groupId>org.apache.httpcomponents</groupId>
                <artifactId>httpclient</artifactId>
            </exclusion>
        </exclusions>
    </dependency>

**2.2 父 POM 统一锁版（根治方案）**

在项目顶级父 POM 中，用 `<dependencyManagement>` 强制锁定关键框架版本：

    <dependencyManagement>
        <dependencies>
            <dependency>
                <groupId>org.springframework.cloud</groupId>
                <artifactId>spring-cloud-dependencies</artifactId>
                <version>2023.0.1</version>
                <type>pom</type>
                <scope>import</scope>
            </dependency>
            <dependency>
                <groupId>com.fasterxml.jackson</groupId>
                <artifactId>jackson-bom</artifactId>
                <version>2.16.1</version>
                <type>pom</type>
                <scope>import</scope>
            </dependency>
            <dependency>
                <groupId>io.netty</groupId>
                <artifactId>netty-bom</artifactId>
                <version>4.1.108.Final</version>
                <type>pom</type>
                <scope>import</scope>
            </dependency>
        </dependencies>
    </dependencyManagement>

作用：从源头杜绝版本碎片化，所有子模块继承统一版本。

**2.3 Maven Shade 重命名（终极手段）**

适用场景：`<exclusions>` 无法解决的情况，如：
- 第三方 SDK 硬编码了 `META-INF/services` 加载。
- 多个 Jar 包中存在全限定名完全相同的类。
- 例如 Netty、Dubbo 等框架的 SPI 机制导致类加载冲突。

    <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-shade-plugin</artifactId>
        <version>3.5.0</version>
        <executions>
            <execution>
                <phase>package</phase>
                <goals>
                    <goal>shade</goal>
                </goals>
                <configuration>
                    <relocations>
                        <relocation>
                            <pattern>com.alibaba</pattern>
                            <shadedPattern>com.mycompany.shaded.alibaba</shadedPattern>
                        </relocation>
                    </relocations>
                </configuration>
            </execution>
        </executions>
    </plugin>

注意：Shade 会增大包体积，非必要不使用。


## 典型报错与根因对照表

| 报错类型 | 典型异常信息 | 根本原因 |
| :--- | :--- | :--- |
| **方法未找到** | `java.lang.NoSuchMethodError` | 代码调用了新版本 API，但实际加载的是老版本 Jar 包（方法签名不匹配） |
| **类未找到** | `java.lang.NoClassDefFoundError` | 编译时存在该类，但运行时类路径中缺失（依赖被排除了，或者版本变更后类被删除/移动） |
| **类定义冲突** | `java.lang.LinkageError` | 同一个类被不同 ClassLoader 加载了两次，或接口实现版本不一致 |
| **抽象方法错误** | `java.lang.AbstractMethodError` | 继承的抽象类/接口在不同版本中方法签名发生了变化 |


## 高频追问与标准答案

### Q1：`mvn dependency:tree` 显示有冲突，但没报错，需要处理吗？

> **必须处理**。因为这是**运行时定时炸弹**。虽然现在加载的版本碰巧兼容，但一旦某个分支代码触发了新 API，立刻 `NoSuchMethodError`。我会在代码评审阶段就强制介入，在父 POM 中统一升到高版本并全量回归测试。

### Q2：Shade 重命名和 Exclude 排除，优先用哪个？

> **优先 Exclude**，因为它轻量，只是去掉不需要的依赖。Shade 是终极手段，只在以下情况使用：
> 1. 依赖无法被排除（硬编码的 SPI 加载，如 `META-INF/services`）。
> 2. 两个不同 Jar 包中包含了全限定名相同的类（如 `com.google.common.util.concurrent` 在不同库中被重复打包）。
>
> Shade 会显著增大包体积，非必要不使用。

### Q3：Spring Boot 项目为什么很少遇到严重的 Jar 包冲突？

> Spring Boot 2.3 开始，`spring-boot-maven-plugin` 的 `repackage` 功能默认会将冲突的第三方依赖 Shade 到 `BOOT-INF/lib` 下做隔离。但业务自己引入的第三方 SDK（如支付宝、微信 SDK）之间仍然可能互斥，这部分需要按上述两步法手动处理。

### Q4：生产环境紧急报 `NoSuchMethodError`，又没法加 JVM 参数重启，怎么快速定位？

> 用 **Arthas** 在线诊断：
>     sc -d java.lang.String      # 查看类加载器信息
>     jad java.lang.String        # 反编译确认方法签名
>
> 几秒钟就能确定 Jar 包来源和代码版本，无需重启。配合 `watch` 命令还可以观测方法入参和返回值，快速确认是哪个版本的方法被调用了。


## 预防性治理（让冲突“不发生”）

| 阶段 | 措施 |
| :--- | :--- |
| **项目初始化** | 使用 Spring Boot BOM + 公司顶级父 POM 统一锁版，子模块只声明 `groupId` + `artifactId`，不声明 `version` |
| **代码评审** | MR 时关注 `pom.xml` 变更，人工检查 `mvn dependency:tree` 的 diff |
| **CI 流水线** | 加入 `mvn dependency:analyze` 和 `mvn dependency:tree` 检查，自动发现未声明的依赖和冲突版本 |
| **定期治理** | 每季度升级一次关键框架版本（如 Spring Boot、Spring Cloud），同步清理老版本依赖 |


## 总结金句

> Jar 包冲突本质是**依赖传递导致的类路径污染**。我的处理策略分两步：**用 `mvn dependency:tree` 精准定位冲突来源，再用 `<exclusions>` 排除 + 父 POM `<dependencyManagement>` 统一锁版**。遇到无法排除的硬编码 SPI 加载时，再用 **Maven Shade 插件做类重命名隔离**。
>
> 最好的治理是**预防**——在项目初始化时就引入公司父 POM，把关键框架版本锁死，让冲突没有机会发生。
