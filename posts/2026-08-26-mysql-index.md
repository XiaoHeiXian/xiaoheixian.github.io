## 一句话概括

索引优化核心是 **“减少回表与扫描范围”**，遵循 **“选列 → 防失效 → 控成本 → 架构降维”** 四层方法论。终极目标是让所有核心查询都能走 `ref` 或 `range` 级别以上的索引，杜绝全表扫。

---

## 四大维度 · 十二条铁律

### 第一维度：选列与排序（建什么样的索引）

**原则 1：最左前缀原则（铁律）**

- 联合索引 `(a, b, c)` 从左到右匹配，遇到范围查询（`>`、`<`、`between`、`like`）停止匹配。
- 示例：
  - `where a = 1 and b = 2 and c = 3` → 用全列 `(a, b, c)`
  - `where a = 1 and c = 3` → 只用 `a`（中间断了 `b`，`c` 失效）
  - `where b = 2 and c = 3` → 完全不走（跳过了 `a`）

**原则 2：高区分度列前置**

- 区分度（Cardinality）高的列放最左，如 `user_id`、`order_no`。
- 低区分度列（如 `status`、`gender`、`is_deleted`）放联合索引的**尾部**。
- 原因：低基数列放前面会导致 B+ 树大量扫描重复值，极易回表。

**原则 3：等值在前，范围在后**

- `=` 查询放联合索引左边，`>`、`<`、`between`、`like` 放右边。
- 原因：**范围查询会截断联合索引**，导致右侧列无法命中。

**原则 4：覆盖索引（核心利器）**

- SELECT 的字段必须全部包含在索引中，实现 `Using index`（不回表）。
- 强制：**核心查询严禁 `select *`**，只带必要字段，建联合索引包住它们。
- 收益：随机 IO 变顺序 IO，查询性能几何级提升。


### 第二维度：规避失效（防止索引“自杀”）

**原则 5：禁止索引列参与函数运算**

- 错误示例：`where DATE(create_time) = '2024-01-01'` → 索引列被函数包裹，全表扫。
- 正确改写：`where create_time >= '2024-01-01' and create_time < '2024-01-02'`

**原则 6：禁止隐式类型转换**

- 字段是 `varchar`，传参传 `int`，或反之。
- 错误示例：`where phone = 13800138000`（`phone` 是 `varchar`）→ 底层触发 `CAST(phone AS int)`，索引列被运算，全表扫。
- 正确写法：`where phone = '13800138000'`

**原则 7：禁止 LIKE 左模糊或全模糊**

- 错误示例：`where name like '%张三'` 或 `where name like '%张三%'`
- 原因：破坏 B+ 树从左到右匹配的有序性。
- 只能右模糊：`where name like '张三%'`（走索引）

**原则 8：避免 OR 连接（或谨慎使用）**

- 错误示例：`where a = 1 or b = 2`
- 原因：除非 `a` 和 `b` 都分别建了索引，否则索引失效（MySQL 5.6 前）。5.6 后引入了索引合并（Index Merge），但仍建议改写成 `UNION` 来获得更好的执行计划。


### 第三维度：维护与成本（DBA 视角）

**原则 9：单表索引数量控制在 5 个以内**

- 索引不是越多越好。每个索引在 `INSERT`、`UPDATE`、`DELETE` 时都要同步维护，影响写入 TPS。
- 建议：单表索引不超过 5~6 个（具体看写入量）。

**原则 10：定期清理冗余索引**

- 已有联合索引 `(a, b)`，再单独建 `(a)` 是多余的（最左前缀原则下 `(a)` 已被覆盖）。
- 工具：`pt-duplicate-key-checker` 可自动检测重复索引。
- 检查项：查看 `information_schema.statistics` 中 `SEQ_IN_INDEX` 的重复情况。

**原则 11：ORDER BY / GROUP BY 走索引排序**

- 让 `order by` 的列尽量在索引中且顺序一致。
- 避免 `Using filesort`（内存/磁盘排序，极其消耗 CPU，数据量大时极为致命）。


### 第四维度：架构降维（高级开发的分水岭）

**原则 12：大表治理——当索引优化走到尽头**

- 当单表数据量突破**千万级**，B+ 树层级超过 3 层，且索引字段已无法再优化时：
  - **冷热分离**：将 3 个月前的历史数据迁移到归档库，热表只保留近期活跃数据。
  - **分库分表**（Sharding-JDBC）：按商户、按时间等分片键水平拆分，降低单表索引树高度。


## 高频追问与标准答案

### Q1：联合索引 `(a, b, c)`，`where a = 1 order by b` 走不走索引？`where a = 1 and b > 1 order by c` 呢？

> - `where a = 1 order by b`：**走索引**，用到了 `a` 和 `b`，`Extra` 显示 `Using index`，直接利用索引有序性完成排序。
> - `where a = 1 and b > 1 order by c`：**只用到 `a` 和 `b`**，`c` 用不上。因为 `b` 是范围查询，截断了联合索引，`Extra` 会出现 `Using filesort`。优化方案：改索引顺序为 `(a, c, b)`，或改成 `b in (值列表) order by c`。

### Q2：区分度很低（如 `status` 只有 0 和 1）的列，建不建索引？

> **绝不单独建**。但可以放在联合索引的**尾部**。例如查询 `where merchant_id = ? and status = 1`，建 `(merchant_id, status)`，让 `merchant_id` 过滤掉绝大部分数据，`status` 配合**索引下推（ICP）** 在引擎层做二次过滤，减少回表。单独给 `status` 建索引成本远大于收益。

### Q3：覆盖索引是什么？和索引下推（ICP）有什么区别？

> - **覆盖索引**：查询所需的字段全部在索引中，直接返回索引数据，**不回表**。表现是 `Extra` 显示 `Using index`。
> - **索引下推（ICP）**：MySQL 5.6+ 引入，在联合索引遍历过程中，**直接在存储引擎层**用索引中的字段进行过滤，把不符合条件的记录提前筛掉，**减少回表次数**。表现是 `Extra` 显示 `Using index condition`。
> - 一句话区分：**覆盖索引是“查索引就够了（不回表）”**，**索引下推是“回表之前先筛一遍（少回表）”**。

### Q4：MySQL 优化器有时候会“弃用”我们的索引去走全表扫，为什么？

> 当优化器判断索引扫描需要回表的行数超过全表行数的 **20%**（经验值）时，它认为全表扫的随机 IO 成本更低。常见于：
> 1. 查询 `status = 1` 且 90% 的数据都是 `status = 1`。
> 2. 索引列区分度极低。
> 优化方向：利用覆盖索引或强制 `force index`（慎用），更根本的是调整索引设计。

### Q5：数据库 CPU 飙高，慢查询日志里全是全表扫，最快怎么处理？

> 应急三步：
> 1. 用 `EXPLAIN` 分析最慢的 TOP 3 SQL，锁定是哪条。
> 2. 看是否能用覆盖索引直接覆盖查询字段。
> 3. 如果 `where` 条件里的字段区分度极低且无法改动，临时用 `force index` 先恢复业务，事后通过冷热分离或增加冗余字段重构查询。


## 总结金句

> 索引优化本质是 **“让查询尽量少读、尽量顺序读”**。我将索引设计归纳为四层：
> - **选列**：最左前缀 + 高基数优先 + 等值在前
> - **防失效**：禁止函数运算、隐式转换、左模糊
> - **控成本**：单表不超 5 索引，杜绝冗余
> - **架构降维**：千万级走冷热分离或分库分表
>
> 最终目标：**核心查询全部做到 `type` 达到 `ref` 以上，`Extra` 不出现 `Using filesort` 和 `Using temporary`。**
