## 一句话概括

慢查询优化遵循 **“先定位 → 再分析 → 后调优”** 三步走。开启慢日志抓 TOP SQL，用 `EXPLAIN` 看执行计划，通过**索引优化、SQL 改写、分表归档**逐级解决。核心目标：**让所有核心查询都走索引，且 type 达到 ref 以上**。


## 核心流程（三步走）

### 第一步：定位（抓出“慢的”）

- 开启 MySQL 慢查询日志（`slow_query_log`）
- 设置阈值（生产通常设为 1 秒，核心库可设为 500ms）：`long_query_time = 1`
- 用 `pt-query-digest` 工具聚合分析，或利用 Skywalking/Prometheus 抓取 TOP N 高耗时 SQL

**原则**：先抓“老虎”，不要对着所有 SQL 盲目优化，优先解决执行频率最高、耗时最长的 TOP SQL。

### 第二步：分析（看懂“怎么查的”）

用 `EXPLAIN`（PostgreSQL 用 `EXPLAIN ANALYZE`）查看执行计划，重点关注以下字段：

| 字段 | 关注点 | 危险信号 |
| :--- | :--- | :--- |
| **type** | 访问类型，从好到坏：`const` > `eq_ref` > `ref` > `range` > `index` > `ALL` | 出现 `ALL`（全表扫）或 `index`（全索引扫）需立即优化 |
| **rows** | 预估扫描行数 | 越大越危险 |
| **Extra** | 额外信息 | 出现 `Using filesort`（文件排序）或 `Using temporary`（临时表）需重点优化 |
| **key** | 实际使用的索引 | 若为 `NULL`，表示未使用索引 |
| **filtered** | 存储引擎层过滤后的数据占比 | 值越低说明索引过滤效果越好，反之需要回表大量数据 |

### 第三步：调优（逐级解决）

调优按成本从低到高分为三个层级：

| 层级 | 手段 | 适用场景 |
| :--- | :--- | :--- |
| **第一层：索引优化** | 建联合索引、覆盖索引、调整索引顺序 | 查询条件明确，但未命中索引或索引效率低 |
| **第二层：SQL 改写** | 深分页改延迟关联、OR 改 UNION、函数运算移至等号右侧 | 索引已存在但 SQL 写法导致索引失效 |
| **第三层：架构降维** | 冷热分离（归档历史数据）、分库分表（Sharding-JDBC）、读写分离 | 单表数据量突破千万级，索引 B+ 树层级超过 3 层 |


## 实战案例一：支付中台（索引 + 分表）

**场景**：统一支付中台订单表日均百万级增长，单表数据量突破千万，慢查询频繁。

**分析**：`EXPLAIN` 后发现单表 `rows` 扫描量极大，B+ 树高度增加导致 IO 剧增，索引优化已到瓶颈。

**方案**：
- 使用 **Sharding-JDBC 按月分表**（`order_202401`、`order_202402`...），以 `create_time` 作为分片键。
- 建立**冷热数据归档**机制：热库保留 3 个月，3 个月前数据迁移至历史库。
- 查询时只查热表，历史查询走单独的历史查询链路。

**结果**：慢查询数量减少 **80%**。


## 实战案例二：缴费项目（多级缓存，从源头卸载）

**场景**：开学季 18 万学生集中缴费，日查询量 200 万+，即使 SQL 命中索引，数据库 CPU 也飙到了 85%。

**分析**：核心查询都是高频重复查询（如学生缴费状态、欠费金额），属于**读多写少**场景，适合用缓存卸载数据库压力。

**方案**：构建 **Caffeine 本地缓存 + Redis 分布式缓存** 的多级缓存架构：
- L1（本地缓存）：Caffeine，缓存热点数据，命中率最高，响应最快。
- L2（分布式缓存）：Redis，跨实例共享，保证数据一致性。
- 缓存更新策略：写入时采用 **Cache-Aside 模式**（先更新 DB，再删除缓存），保证最终一致性。

**结果**：
- 缓存命中率：**98%**
- 数据库 CPU 峰值：从 **85% 降至 35%**
- 成本下降：**60%**
- 核心接口 TP99：从 **6.2s 优化到 90ms**


## 高频追问与标准答案

### Q1：`EXPLAIN` 中 `type` 从 `ALL` → `index` → `range` → `ref` → `eq_ref` → `const` 的区别？

> 按性能从左到右递增：
> - `const`：主键或唯一键查一行（最好）。
> - `eq_ref`：联表查询，被驱动表使用主键或唯一键关联（极好）。
> - `ref`：普通索引等值匹配（良好）。
> - `range`：范围查询（及格线）。
> - `index`：索引全扫描（较差，需要优化）。
> - `ALL`：全表扫描（最差，必须优化）。

### Q2：深分页（`limit 100000, 10`）怎么优化？

> 三种方案：
> 1. **延迟关联**：先走覆盖索引查出主键 ID，再 JOIN 回原表取完整数据。
> 2. **游标分页（Seek Method）**：记录上一页最后一条 ID，下一页用 `where id > lastId limit 10`。
> 3. **子查询优化**：`where id >= (select id from table order by id limit 100000, 1) limit 10`
>
> 推荐方案 2，对业务改动最小且性能最优，在支付流水和订单列表里极其常用。

### Q3：分表和加索引，优先选哪个？

> 看数据量阈值：
> - **百万级以内**：优先**索引优化 + SQL 改写**（成本最低）。
> - **千万级以上**且索引 B+ 树层级已超过 3 层，分表是必选项。
> - 核心口诀：**能用索引解决的，不动分表；当索引优化遇到瓶颈时，分表是降维打击。**

### Q4：多级缓存怎么保证数据一致性？

> 采用 **Cache-Aside 模式**：
> - **读**：先查缓存，命中则直接返回；未命中则查 DB，回填缓存。
> - **写**：先更新 DB，再**删除**缓存（而非更新缓存），下次读时重建。
> - 为什么删除而非更新？防止并发写导致缓存脏数据。
> - 极端场景（如支付状态变更）可增加**延迟双删**（更新 DB 后先删缓存，延迟 500ms 后再删一次）保证最终一致性。

### Q5：数据库 CPU 飙高，慢查询日志里全是全表扫，最快怎么应急处理？

> 应急三步：
> 1. 用 `EXPLAIN` 分析最慢的 TOP 3 SQL，锁定是哪条。
> 2. 看是否能用**覆盖索引**直接覆盖查询字段。
> 3. 如果 `where` 条件里的字段区分度极低且无法改动，临时用 `force index` 先恢复业务，事后通过冷热分离或增加冗余字段重构查询。


## 总结金句

> 慢查询优化是一场 **“从数据库到应用层”的系统性工程**。我遵循三步走方法论：
> 1. **定位**：用慢日志 + `pt-query-digest` 抓出 TOP SQL
> 2. **分析**：用 `EXPLAIN` 锁定全表扫、文件排序、临时表等罪魁祸首
> 3. **调优**：先索引、再改写、最后分表归档
>
> 更高阶的思路是 **“上医治未病”**——在架构设计阶段就规划好分表策略和缓存兜底，上线前用 `EXPLAIN` 评审所有核心 SQL，确保每个查询都走在索引上。
