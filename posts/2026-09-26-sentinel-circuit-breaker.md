1、定义

熔断降级是 Sentinel 用来防止服务雪崩的核心容错机制，当下游接口、远程服务出现响应太慢、超时多、异常率高时，Sentinel 自动切断调用链路，短时间内不再调用真实业务接口，直接执行兜底降级逻辑，快速释放服务器线程资源，避免故障向上蔓延。

1）熔断

类比电路保险丝：
电路短路频繁 -> 保险丝熔断 -> 保护整机
服务频繁超时 / 报错 -> Sentinel 熔断 -> 保护整个微服务链路

2）触发条件

（1）慢调用比例：请求耗时超过设定最大 RT 的比例达标，触发熔断
（2）异常比例：接口报错比例达标，触发熔断
（3）异常数：短时间异常请求数量达标，触发熔断

3）熔断后表现

- 不再执行业务代码（不再走超时 / 报错逻辑）
- 直接返回兜底提示
- 线程立刻释放，不会阻塞积压
- 熔断窗口时间结束后，自动半开探测，尝试恢复正常调用

4）熔断与限流的区别

- 限流：防突发高并发流量（流量太大拦住）
- 熔断：防下游故障雪崩（服务坏了主动断开）

2、实践

【案例一】：慢比例调用降级

场景说明：接口响应缓慢、大量请求超时，不及时拦截会导致线程积压、服务雪崩，通过慢调用比例规则自动熔断，保护服务。

降级策略：慢调用比例
最大 RT：500ms（单请求响应耗时超过 500ms，判定为慢调用）
比例阈值：0.5（50%）（慢调用请求占总请求比例≥50%，触发熔断）
最小请求数：5（统计周期内至少 5 次请求，才会判定是否熔断，避免统计误差）
熔断时长：5 秒（触发熔断后，5 秒内直接降级，不执行业务代码）

规则解读：Sentinel 会统计近 1 秒的请求数据：满足总请求数≥5 + 超 500ms 慢调用占比≥50% 两个条件，立即开启 5 秒熔断窗口。熔断期间所有请求直接走降级兜底，不会执行逻辑，快速释放线程。

（1）业务接口

在 mall-test-service 的 OrderController 添加方法：

    @GetMapping("/degrade")
    public String degradeTest() throws InterruptedException {
        log.info("降级测试");
        // 模拟业务处理耗时：固定 800ms，超过阈值 500ms，判定为慢调用
        Thread.sleep(800);
        return "接口正常执行，业务请求处理完成";
    }

（2）规则配置

按案例需求配置：

    资源名：/order/errorDegrade
    熔断策略：异常比例（注：图片配置界面选中的是异常比例，但案例文字描述为慢调用比例，此处按图片实际配置记录）
    比例阈值：0.3
    熔断时长：5s
    最小请求数：5
    统计时长：1000ms

（3）测试

注意：在测试前先关闭全局异常处理，控制器抛出的异常被全局异常处理器捕获并处理了。

使用 Jmeter 测试，重新创建线程组（线程数 100，启动时间 10，循环次数 1），添加 HTTP 请求：/order/errorDegrade

💡 **速记**

**【什么是熔断降级？】**
Sentinel 防止服务雪崩的核心容错机制。当下游服务响应慢、超时多、异常率高时，自动切断调用链路，直接执行兜底降级逻辑，快速释放线程资源。

**【三大触发条件】**
1. **慢调用比例**：请求耗时超过最大 RT 的比例达标（如 50% 请求超过 500ms）。
2. **异常比例**：接口报错比例达标。
3. **异常数**：短时间异常请求数量达标。

**【熔断后的四大表现】**
1. 不执行业务代码（不走超时/报错逻辑）。
2. 直接返回兜底提示（降级逻辑）。
3. 线程立刻释放，不阻塞积压。
4. 熔断窗口结束后，自动半开探测，尝试恢复。

**【熔断与限流的本质区别】**
*   **限流**：防大流量（流量太大拦住）。
*   **熔断**：防下游故障（服务坏了主动断开）。

**【实战配置核心参数（案例一）】**
*   降级策略：慢调用比例
*   最大 RT：500ms
*   比例阈值：0.5（50%）
*   最小请求数：5
*   熔断时长：5秒
*   规则解读：近1秒内，总请求≥5 且 慢调用占比≥50%，触发5秒熔断。熔断期间走降级逻辑，不执行业务代码。
