2）事务缺失导致的问题

从以上两个场景的测试发现：

（1）事务管控缺失：订单主、明细入库未封装在同一数据库事务，无法实现操作要么全成功、要么全回滚，出现部分写脏数据。产生“有明细无主订单”的无效数据，破坏订单业务完整关联关系，会引发对账、统计、下游业务逻辑错误。

（2）跨服务分布式事务无保障：订单本地库与远程库存服务分属不同数据源，本地数据库事务无法联动回滚库存操作。远程调用扣库存时报错/超时/调用失败时，订单数据持久化入库，系统无法自动识别“存在有效订单，但对应商品库存未扣减/扣减不全”的异常数据，出现订单已生成、库存数量不匹配的数据不一致。

3）解决方案

（1）使用数据库事务统一包裹主、明细新增逻辑，保证原子性。
（2）引入分布式事务框架（Seata AT/TCC）或可靠消息最终一致性方案，保证订单创建、库存扣减同时成功或同时回滚。
（3）新增操作日志，记录订单入库全流程，便于异常排查。

2、什么是事务

1）定义

事务（Transaction）是访问并可能更新数据库中各项数据项的一个程序执行单元（unit）。事务由事务开始（begin transaction）和事务结束（end transaction）之间执行的全体操作组成。是一个不可分割的数据库操作序列，也是数据库并发控制的基本单位，其执行的结果必须使数据库从一种一致性状态变到另一种一致性状态。

事务结束有两种：事务中的步骤全部成功执行时，提交事务。如果其中一个失败，那么将会发生回滚操作，并且撤销之前的所有操作。也就是说，事务内的语句，要么全部执行成功，要么全部执行失败。

下图是一个银行转账事务流程图，描述了从A账户向B账户转账100元的事务过程：

![银行转账事务流程图](https://xiaoheixian.github.io/posts/assets/273_65.png)

（开始）-> 余额1000元 -> 转出100元 -> （判断：余额修改成功？）
- 是(Y) -> 余额900元 -> 余额100元 -> 转入100元 -> （判断：余额修改成功？）
- 是(Y) -> 余额200元 -> 提交 -> 结束
- 否(N) -> 回滚 -> 回到开始余额1000元

2）事务的特性

事务具有四个特征：原子性、一致性、隔离性和持久性。这四个特征通常称为 ACID。

（1）原子性(Atomicity)
一个事务(transaction)中的所有操作，要么全部完成，要么全部不完成，不会结束在中间某个环节。事务在执行过程中发生错误，会被回滚(Rollback) 到事务开始前的状态，就像这个事务从来没有执行过一样。

（2）一致性(Consistency)
事务的一致性指的是在一个事务执行之前和执行之后数据库都必须处于一致性状态。即事务必须使数据库从一个一致性状态变换到另一个一致性状态。
如果事务成功地完成，那么系统中所有变化将正确地应用，系统处于有效状态。
如果在事务中出现错误，那么系统中的所有变化将自动地回滚，系统返回到原始状态。

（3）隔离性(Isolation)
指的是在并发环境中，当不同的事务同时操纵相同的数据时，每个事务都有各自的完整数据空间。由并发事务所做的修改必须与任何其他并发事务所做的修改隔离。事务查看数据更新时，数据所处的状态要么是另一事务修改它之前的状态，要么是另一事务修改它之后的状态，事务不会查看到中间状态的数据。

（4）持久性(Durability)
指的是只要事务成功结束，它对数据库所做的更新就必须保存下来。即使发生系统崩溃，重新启动数据库系统后，数据库还能恢复到事务成功结束时的状态。

3）数据库并发事务（冲突）产生的问题

（1）脏读
脏读就是读取事务未提交数据（内存中数据）。指当一个事务 A 正在访问数据，并且对数据进行了修改，而这种修改还没有提交到数据库中，这时，另外一个事务 B 也访问这个数据，读了未提交事务操作的数据，然后使用了这个脏数据。

| 事务时间 | 事务A | 事务B |
| :--- | :--- | :--- |
| T0 | 开始事务 | |
| T1 | (读) 余额: 100 | |
| T2 | (存 50) 余额: 100+50=150 | 开始事务 |
| T3 | | (读) 余额: 150 |
| T4 | | (取 80) 余额: 150-80=70 |
| T5 | | 提交 |
| T6 | 回滚 | |

从上表可以看出，事务 B 读取了事务 A 的一条脏数据。

（2）不可重复读
不可重复读指的是前后多次读取数据不一致。在事务 A 中先后多次读取同一个数据，读取的结果不一样，因为另外一个事务也访问该同一数据，并且可能修改这个数据，这种现象称为不可重复读。
脏读与不可重复读的区别在于：前者读到的是其他事务未提交的数据，后者读到的是其他事务已提交的数据。

| 事务时间 | 事务A | 事务B |
| :--- | :--- | :--- |
| T0 | 开始事务 | |
| T1 | (读) 余额: 100 | |
| T2 | (存 50) 余额: 100+50=150 | 开始事务 |
| T3 | | (读) 余额: 100 |
| T4 | | (取 80) 余额: 100-80=20 |
| T5 | 提交 | |
| T6 | | (读) 余额: 150 |

从上表可以看出，事务 B 两次读取的数据不一致。

（3）幻读
幻读是指前后多次读取到不一致的数据。在事务 A 中按照某个条件先后两次查询数据库，两次查询结果的条数不同，这种现象称为幻读。
不可重复读与幻读的区别可以通俗的理解为：前者是数据变了，后者是数据的行数变了。通俗点就是已提交事务 B 对事务 A 产生的影响，导致 B 执行有误，这个影响叫做“幻读”。不可重复读针对的是 update 操作（加行锁），而幻读针对的是 insert 和 delete 操作（加表锁）。

（4）丢失更新
丢失更新是指两个事务同时读取同一个数据，然后进行修改，后提交的数据会覆盖先提交的数据。

| 事务时间 | 事务A | 事务B |
| :--- | :--- | :--- |
| T0 | 开始事务 | |
| T1 | (读) 余额: 100 | |
| T2 | (存 50) 余额: 100+50=150 | 开始事务 |
| T3 | | (读) 余额: 100 |
| T4 | | (取 80) 余额: 100-80=20 |
| T5 | | 提交 |
| T6 | 提交 | |

从上表可以看出，事务 A 提交覆盖了事务 B 的提交的数据。

4）事务的隔离级别

并发的事务可能导致其他事务读脏数据、不可重复读、幻读等问题。那么如何解决这些问题呢？隔离性可以防止多个事务并发执行时由于交叉执行而导致数据的不一致的问题。

（1）读未提交(Read Uncommitted)
读未提交情况下，可以读取到其他事务还未提交的数据，多次读取结果不一样，出现了脏读、不可重复读的情况。这种情况下 select 语句不加锁，所以这是并发最高，一致性最差的隔离级别。

（2）读已提交(Read Committed)
这是大多数数据库系统的默认隔离级别（MySQL 除外）。读已提交情况下，无法读取到其他事务还未提交的数据，可以读取到其他事务已经提交的数据，多次读取结果不一样，不会出现脏读和幻读，但出现不可重复读。这种隔离级别用的比较多，也是互联网业务最常用的隔离级别。

（3）可重复读(Repeated Read)
可重复读是 InnoDB (MySQL) 默认的隔离级别。保证了在同一事务中先后执行的多次查询将返回同一结果，看到的每行的记录的结果是一致的，不受其他事务的影响。但是这种级别下有可能发生幻读。

（4）串行化(Serializable)
不允许事务并发执行，强制事务串行执行。就是在读取的每一行数据上都加上了锁，读写相互都会阻塞，所以效率很低。这种隔离级别最高，是最安全的，但是性能最低，不会出现脏读，不可重复读，幻读。

任何事务机制在实现时，都应该考虑事务的 ACID 特性，包括：本地事务、分布式事务，即使不能很好的满足，也要考虑支持到什么程度。

💡 **速记**

**【问题引入（核心踩分点）】**
1. **本地事务缺失**：订单明细先入库，订单主表入库时抛异常 -> 产生“有明细无主单”的脏数据。
2. **分布式事务缺失**：订单入库成功，但远程扣减库存时抛异常 -> 订单生成但库存未扣减。
3. **解决方案**：本地数据库事务（@Transactional）、分布式事务框架（Seata AT/TCC）、可靠消息最终一致性、操作日志。

**【事务定义与 ACID】**
*   **定义**：不可分割的数据库操作序列，要么全成功，要么全失败（回滚）。
*   **原子性 (Atomicity)**：全成功或全回滚。
*   **一致性 (Consistency)**：执行前后数据库都处于一致性状态。
*   **隔离性 (Isolation)**：并发事务互不干扰。
*   **持久性 (Durability)**：提交后数据永久保存。

**【并发事务四大问题】**
1. **脏读**：读到了其他事务**未提交**的数据。
2. **不可重复读**：前后多次读取结果不一致（其他事务修改并**提交**了），针对 **update**（行锁）。
3. **幻读**：前后多次读取数据条数不一致（其他事务**插入/删除**并提交了），针对 **insert/delete**（表锁）。
4. **丢失更新**：后提交的事务覆盖了先提交事务的数据。

**【四大隔离级别（高频考点）】**
1. **读未提交 (Read Uncommitted)**：不加锁，并发最高，一致性最差，出现脏读、不可重复读。
2. **读已提交 (Read Committed)**：默认级别（除MySQL），避免脏读，出现不可重复读。互联网最常用。
3. **可重复读 (Repeated Read)**：MySQL默认，避免脏读、不可重复读，可能出现幻读。
4. **串行化 (Serializable)**：加锁串行执行，效率最低，最安全，避免所有并发问题。
