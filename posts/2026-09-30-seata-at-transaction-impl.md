结合 Seata 的 AT 模式，在项目中为“生成订单、库存扣减”这个典型电商场景实现了一套无侵入的分布式事务方案。

简单来说，只需要在订单服务的下单方法上添加一个 @GlobalTransactional 注解，Seata 就会自动帮你协调这两个服务，保证它们要么一起成功，要么一起回滚。

（1）拆解一下它是如何做到的：

Seata 的核心角色：

TM (事务管理器)：负责开启、提交或回滚全局事务。在我们的场景中，发起下单请求的订单服务就是 TM。

RM (资源管理器)：负责管理分支事务，即执行具体的数据库操作，并向 TC 汇报。订单服务、库存服务就是 RM。

TC (事务协调者)：独立的服务端，是全局事务的“大脑”，负责维护事务状态，协调所有 RM 进行提交或回滚。

（2）这个分布式事务的完整执行过程分为两个阶段：

第一阶段：所有服务执行本地事务

订单服务（TM+RM）：

① 接收到下单请求，@GlobalTransactional 开启全局事务，获取 XID。

② 执行生成订单的 SQL 前，Seata 生成前镜像（订单明细、订单表修改前的状态，因为是 INSERT，前镜像为空）。

③ 执行 SQL，生成订单和订单明细记录。Seata 生成后镜像（新插入的订单记录数据）。

④ 将前镜像、后镜像、SQL 信息保存到订单库的 UNDO_LOG 表。

⑤ 订单服务的本地事务提交，订单数据正式落库。

库存服务（RM）：

① 接收到带 XID 的 RPC 请求，注册分支事务。

② 执行扣减库存的 SQL，生成前镜像（扣减前的库存数量）和后镜像（扣减后的库存数量）。

③ 将前、后镜像保存到 UNDO_LOG 表。

④ 本地事务提交，库存扣减生效。

此时，所有服务的数据都已经在各自数据库中发生了变更，并且每个服务都在自己的 UNDO_LOG 表中存好了可以回滚的前后镜像（后悔药）。

第二阶段：全局决议

成功场景（全局提交）：

① TM（订单服务）向 TC 报告成功，TC 通知所有 RM（包括订单自身）二阶段提交。

② 所有 RM（订单、库存）做同一件事：异步批量删除自己 UNDO_LOG 表中对应的记录，释放全局锁。

失败场景（全局回滚）：

① 假设库存扣减失败，TM 向 TC 报告回滚。TC 通知所有 RM（订单、库存）回滚。

② 所有 RM 会做同一件事：根据 UNDO_LOG 记录，进行反向补偿。

- 订单服务：因为是 INSERT 操作，回滚 SQL 就是 DELETE FROM order WHERE id = xxx（根据前镜像判断记录是否存在）。

- 库存服务：如果是 UPDATE 扣减，回滚 SQL 就是 UPDATE stock SET count = 前镜像值 WHERE id = xxx。

③ 恢复数据后，删除自己的 UNDO_LOG，释放全局锁。

为什么订单服务也需要全局锁？

你可能会疑问：订单是 INSERT 新增，又不是修改库存这种竞争性数据，为什么还要加全局锁？

这是因为隔离性的要求。假设在全局事务提交前，另一个分布式事务试图修改或查询这条订单数据，Seata 需要通过全局锁来保证：在第一个事务最终决议（提交或回滚）之前，其他事务不能读取或修改这条未确定的订单数据，从而防止脏读和脏写。

💡 **速记**

**【Seata AT 模式核心角色】**
*   **TM (事务管理器)**：发起全局事务（如订单服务）。
*   **RM (资源管理器)**：执行分支事务，操作数据库（如订单服务、库存服务）。
*   **TC (事务协调者)**：独立服务端，协调全局提交或回滚。

**【AT 模式两阶段执行流程】**
*   **第一阶段（本地事务）**：
    1. 获取全局锁，生成 XID。
    2. 执行 SQL 前生成**前镜像**（INSERT 为空，UPDATE 为原值）。
    3. 执行 SQL 后生成**后镜像**（新数据）。
    4. 将前后镜像及 SQL 写入 **UNDO_LOG** 表。
    5. 提交本地事务。
*   **第二阶段（全局决议）**：
    *   **全局提交**：TC 通知 RM，异步删除 UNDO_LOG，释放全局锁。
    *   **全局回滚**：TC 通知 RM，根据 UNDO_LOG 反向补偿。
        *   INSERT 回滚：`DELETE FROM order WHERE id = xxx`
        *   UPDATE 回滚：`UPDATE stock SET count = 前镜像值 WHERE id = xxx`
        *   恢复后删除 UNDO_LOG，释放全局锁。

**【为什么需要全局锁？】**
*   保证隔离性，防止在全局事务提交前，其他事务读取或修改这条未确定的订单数据，避免脏读和脏写。
