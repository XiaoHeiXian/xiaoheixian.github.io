## 1、为什么要消息去重

RocketMQ 的消息去重，本质上是在业务层面实现消息的幂等消费。

因为 RocketMQ 的设计哲学是“至少消费一次”（At-least-once），它保证消息不丢失，但并不保证消息不重复。

换句话说，消息重复是一个设计上承认会存在的问题，我们需要在消费端主动解决它。

## 2、消息重复的根源

理解消息为什么重复，是去重的前提。重复通常发生在两个环节：

（1）生产者发送阶段：

生产者发送消息后，因网络闪断未收到服务端的成功响应（ASK），会触发重试机制再次发送，导致 Broker 中存在多条内容相同的消息。

（2）消费者消费阶段：

消费者处理完业务逻辑后，因网络问题未能及时向 Broker 提交消费进度（Offset），Broker 会认为消费失败并重新投递该消息。

（3）其他场景：

如消费者组发生重平衡（Rebalance）、Broker 异常重启导致 Offset 未持久化、主从同步失败等，都可能造成重复消费。

## 3、消息重复带来的危害

消息重复带来的危害是多维度、系统性的，绝不仅仅是“多做一次无用功”那么简单。

在分布式系统中，它像一颗隐蔽的定时炸弹，可能从数据、业务、资金、系统四个层面引发严重问题。

（1）资金与资产损失（最致命的危害）

重复扣款：用户下单支付，因网络问题导致支付的消息被重复消费，系统可能会再次执行扣款逻辑，导致用户账户被重复扣费。

重复发放权益：用户完成一笔订单应获得一次积分或一张优惠券。消息重复会导致系统给用户发放多倍积分或优惠券，造成营销成本严重超支。

重复计数：在活动场景下，用户的一次有效行为（如点击、签到）应该只计数一次。重复消费会导致活动数据虚高，影响活动效果评估，甚至被“羊毛党”利用规则漏洞进行刷单。

（2）数据一致性与逻辑错误

数据重复插入：在“订单创建”等场景中，如果业务代码未做校验，重复消费会导致数据库插入多条完全相同的订单记录，造成数据冗余和统计失真。

状态机紊乱：对于订单状态流转（如 待支付 -> 已支付 -> 已发货），如果“已支付”消息被重复处理，可能会尝试将一个“已发货”的订单状态再次修改为“已支付”，导致状态机异常和业务流程中断。

库存超卖：在秒杀或库存扣减场景中，重复的“下单成功”消息可能导致系统重复扣减库存，最终出现库存为负数（超卖）的严重问题。

（3）资源浪费与性能下降

CPU 与内存浪费：每条消息的消费都需要经历网络传输、反序列化、业务逻辑执行等过程，重复消息会白白占用这些计算资源。

下游服务压力：如果消费逻辑中调用了第三方接口（如短信、邮件发送），重复调用不仅浪费资源，还可能触发服务商的限流策略，导致正常请求被拒绝。

数据库连接池耗尽：重复消费会发起更多的数据库查询和写入操作，可能耗尽数据库连接池，导致正常业务请求无法执行。

（4）业务错乱与客户投诉

重复通知骚扰：例如“发货通知”短信或邮件被重复发送，会严重影响用户体验。

业务状态混乱：例如，一个“退款成功”的消息被重复消费，可能系统会尝试对一个已退款的订单再次发起退款，导致业务流程卡死。

数据报表统计错误：业务报表（如日活）依赖消息进行计数。重复消息会导致所有统计指标虚高，影响管理层的决策判断。

总而言之，消息重复是一个必须从设计层面彻底解决的问题，而不是可以容忍的小概率事件。

这也是为什么在 RocketMQ 等消息中间件的实践指南中，“幂等性设计”永远是消费者端最重要的原则之一。

## 4、核心解决方案

解决重复消费问题的核心思路是：无论收到多少次重复消息，业务处理的结果都应该是唯一的。

业界最通用的做法是使用业务的唯一标识（如订单 ID）作为去重依据。

为什么不直接使用 Message ID？

虽然每条消息都有唯一的 Message ID，但在生产者发送失败重试的场景下，同一条业务消息可能会生成不同的 Message ID。

因此，Message ID 不能作为可靠的去重依据。

解决方案的核心，就是在消费端实现幂等（1ⁿ=1）处理（即同一条消息被消费多次，产生的结果与消费一次完全相同），具体方案可以结合业务唯一 ID 和数据库唯一索引或 Redis 锁来实现。

## 5、流程图文字推演

根据文章逻辑，消息重复的经典触发链路可以推演如下：

生产者发送消息 --> 网络闪断未收到 ASK 响应 --> 触发重试机制 --> Broker 中存在多条相同消息

消费者拉取消息 --> 处理完业务逻辑 --> 提交 Offset 时网络异常 --> Broker 认为消费失败 --> 重新投递消息 --> 消费者再次消费

消费者组发生 Rebalance --> Offset 未及时持久化 --> 消息被重新投递

💡 **速记**

**【核心考点】**

RocketMQ 保证 At-least-once，不保证不重复，必须在消费端做幂等。

**【高频逻辑链】**

重复根源（生产重试 + 消费 Offset 提交失败） --> 多重危害（资金、数据、资源、业务） --> 核心解法（业务唯一 ID + Redis 锁 / 数据库唯一索引）。

**【关键避坑】**

Message ID 在重试场景下会变化，绝对不能作为去重依据。
