事务消息是 RocketMQ 提供的非常重要的一个特性，可以利用事务消息轻松地实现分布式事务。

## 1、核心概念

RocketMQ 在其消息定义的基础上，对事务消息扩展了两个相关的概念：

（1）Half(Prepare) Message——半消息（预处理消息）

半消息是一种特殊的消息类型，该状态的消息暂时不能被 Consumer 消费。

当一条事务消息被成功投递到 Broker 上，但是 Broker 并没有接收到 Producer 发出的二次确认时，该事务消息就处于“暂时不可被消费”状态，该状态的事务消息被称为半消息。

（2）Message Status Check——消息状态回查

由于网络抖动（是指在网络传输过程中，数据包的到达时间相对于其发送时间存在一定的波动和变化。这种波动和变化可能导致接收端在处理数据包时出现时间上的不确定性和不稳定性，从而影响网络应用的性能和质量，主要是在队列中等待时间过长）、Producer 重启等原因，可能导致 Producer 向 Broker 发送的二次确认消息没有成功送达。

如果 Broker 检测到某条事务消息长时间处于半消息状态，则会主动向 Producer 端发起回查操作，查询该事务消息在 Producer 端的事务状态（Commit 或 Rollback）。

可以看出，Message Status Check 主要用来解决分布式事务中的超时问题。

（3）事务 ID

RocketMQ 中的事务 ID（Transaction ID）和消息的 key 都是用来识别消息的唯一标识。

事务 ID（Transaction ID）：在 RocketMQ 中，当你使用事务消息特性时，会为每个事务创建一个事务 ID。这个 ID 用于确保事务消息的唯一性，即使是在消息被提交之后，也能通过这个 ID 找到对应的消息。

## 2、事务流程

事务消息采用两阶段提交（2PC）模型：

阶段一（发送预备消息）：生产者发送半事务消息至消息队列，此时消息对消费者不可见。

阶段二（事务状态确认）：生产者执行本地事务后，向消息队列提交 Commit 或 Rollback 指令，决定消息是否投递。

② prepare 消息发送成功后，应用模块执行数据库事务（本地事务）。

③ 根据数据库事务执行的结果，再返回 Commit 或 Rollback 给 MQ。

④ 如果是 Commit，MQ 把消息下发给 Consumer 端，如果是 Rollback，直接删掉 prepare 消息。

⑤ 第 3 步的执行结果如果没响应，或是超时的，启动定时任务回查事务状态（最多重试 15 次，超过了默认丢弃此消息），处理结果同第 4 步。

⑥ MQ 消费的成功机制由 MQ 自己保证。

## 3、事务回查

### 1）消息回查的作用

事务消息回查机制在分布式系统中具有关键作用，其重要性主要体现在以下方面：

（1）解决事务状态不确定性

当生产者发送预备消息后，可能因服务崩溃、网络故障或事务执行超导致无法主动提交最终状态。此时回查机制通过消息队列定时扫描未确认的半事务消息，主动向生产者发起状态查询，确保每条消息都能获得确定性处理结果（提交或回滚）。

例如在支付成功后发送积分场景中，若支付服务宕机未提交事务状态，回查机制可触发二次确认，避免积分漏发或重复发放。

（2）保障系统可用性

防止消息堵塞：若未实现回查机制，异常场景下大量半事务消息会长期滞留队列，占用存储资源并阻塞后续消息处理。

容错能力增强：通过失败重试策略（如 RocketMQ 默认 15 次回查），即使首次状态查询失败也能通过后续重试恢复处理流程，降低单点故障影响。

（3）实现最终一致性

兜底策略支撑：回查机制作为两阶段提交（2PC）的补充，在生产者未响应时通过预设规则（如超时自动回滚）或业务逻辑重试，确保跨系统操作的最终一致性。

数据修复能力：结合事务日志，回查可通过唯一事务 ID 关联业务状态，修复因异步处理导致的数据不一致问题。

（4）减少人工介入

自动化处理闭环：消息队列自动触发回查流程，无需人工干预未确认消息状态，降低运维复杂度。

实时监控集成：通过回查失败告警（如达到最大重试次数）可快速定位异常事务，提升系统可观测性。

无回查机制的系统需人工介入处理超时消息，而具备回查能力的系统（如 RocketMQ）通过内置状态检测与恢复机制，显著提升分布式事务的可靠性与处理效率。

### 2）回查触发条件

若生产者未在指定时间内（如 RocketMQ 默认 60 秒）提交事务状态，消息队列触发回查流程，向生产者发起事务状态查询请求。

注意，回查请求可能多次触发，需保证状态查询逻辑的幂等性。

## 4、流程图文字推演

根据事务消息的时序图，整个分布式事务的执行链路可以推演如下：

事务生产者(Order Service) --> 发送半事务消息(Half Message) --> RocketMQ Broker 暂存消息(对消费者不可见) --> Broker 返回发送成功(Ack) --> 生产者执行本地事务(修改订单状态) --> 根据本地事务执行结果

本地事务成功 --> 二次确认：Commit --> Broker 将消息变为可见 --> 投递给消费者(Account Service) --> 消费者执行本地业务(增加余额)

本地事务失败 --> 二次确认：Rollback --> Broker 删除消息，不投递

网络异常/超时，二次确认未送达 --> Broker 定时发起事务状态回查 --> 生产者返回本地事务执行结果 --> Broker 根据回查结果决定 Commit 或 Rollback

💡 **速记**

【核心考点】

事务消息通过两阶段提交（2PC）实现分布式事务：先发送半消息（Prepare），执行本地事务后再进行二次确认（Commit 或 Rollback）。

半消息对消费者不可见，只有收到 Commit 后才会被投递；Rollback 则直接删除消息。

【高频逻辑链】

执行流程：发送 Prepare 消息 --> 执行本地事务 --> 提交 Commit/Rollback --> Commit 则投递，Rollback 则删除 --> 超时未确认则触发回查（默认 60 秒，最多 15 次）。

回查作用：解决状态不确定性、防止消息堵塞、实现最终一致性、减少人工介入。

【关键避坑】

回查请求可能多次触发，消费端与回查逻辑必须保证幂等性。

回查超过最大重试次数（默认 15 次）仍未获得明确状态时，Broker 默认会丢弃该消息。
