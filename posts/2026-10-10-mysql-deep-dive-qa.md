## 1、表设计规范与 SPU/SKU 拆分

问：商城项目里为什么要将商品拆分成 SPU、SKU 两张表？团队统一了哪些建表规范？为什么生产环境普遍禁用物理外键？

答：SPU 存储商品型号、图文基础信息，SKU 是具体售卖规格，如果合并成单表会产生大量文本冗余，更新商品详情会批量锁多条规格行，并发性能极差。

我们小组项目启动前就对大厂建表规范：所有表统一增加 deleted 逻辑删除字段、create_time 创建时间、update_time 更新时间，全部使用下划线命名、统一 utf8mb4 字符集，所有 SQL 统一托管 Git，新增表必须由我做 SQL 评审才能上线。

物理外键在批量操作时会触发表锁，严重影响并发性能，所以团队约定全部在业务代码做关联校验，完全不使用数据库物理外键。

## 2、联合索引设计与索引失效

问：商城商品多条件联合索引是怎么设计的？日常开发中会遇到哪些索引失效场景，团队是怎么避免乱建索引的问题？

答：针对用户高频筛选的一级分类、二级分类、三级分类和品牌四个字段，我们设计了联合索引 idx_cat1_cat2_cat3_brand，完全遵循最左前缀原则。

常见的索引失效场景包括：索引字段做运算、前级模糊查询%xx、or 两边字段未全部加索引、隐式类型转换、跳过联合索引最左侧前缀字段。

我们团队有明确的索引管理规范：所有新增 SQL 必须先执行 explain 验证执行计划，禁止私自新建索引，每周统一全库扫描清理无效冗余索引，避免索引过多拖慢写入性能。

## 3、联合索引无法覆盖品牌查询的优化

问：如果用户只传品牌不带分类查询，这个联合索引就用不上了，你们是怎么优化这个场景的？

答：我们小组当时讨论了两套落地方案，一套是新增单列品牌索引，第二套是前端页面默认携带当前选中的一级分类，双方案并行兼顾查询性能与索引维护成本，最终我们选了第二套为主、单列索引为辅的策略，整体性能最优。

## 4、InnoDB 索引结构与聚集/二级/覆盖索引

问：InnoDB 为什么选用 B+树作为索引结构？聚集索引、二级索引、覆盖索引三者区别是什么？

答：二叉树、普通 B 树层级太深，磁盘 IO 次数多查询性能差，B+树非叶子节点仅存储索引字段，叶子节点存储完整数据+双向链表，分页、区间查询效率远高于其他数据结构。

主键聚集索引查询数据不需要回表，直接通过主键拿到完整数据；品牌这类普通二级索引拿到的是主键 ID，还需要回表查询聚集索引才能拿到完整字段；列表查询场景下我们会强制使用覆盖索引，只查询索引包含的字段，不需要回表，大幅减少 IO 消耗。

## 5、深分页优化

问：limit 10000,10 这类深分页查询非常缓慢，你们团队统一了什么分页规范解决这个问题？

答：偏移量大的时候 MySQL 会扫描前面 10000 条数据再直接丢弃，IO 消耗非常高。

我们团队完全统一使用主键游标分页，前端传递上一页最大的 sku_id，直接通过主键范围查询下一页数据，完全禁止超大偏移量的分页，同时首页热门商品列表做缓存进一步优化查询性能。

## 6、事务隔离级别与秒杀幻读

问：四大事务隔离级别分别是什么？秒杀场景下为什么会出现幻读？

答：四大事务隔离级别分别是读未提交、读已提交、可重复读、串行化，InnoDB 默认使用可重复读隔离级别。

秒杀高并发场景下大量事务同时读取库存，可重复读隔离级别下没有加行锁的读操作就会出现幻读，多个事务同时读到相同的库存剩余值，后续操作就会出现库存超卖问题。

## 7、水平分表方案

问：如果订单数据量达到千万级，你们会怎么设计水平分表方案？你们小组有没有开展过相关的技术分享对齐规范？

答：我们会以 user_id 做哈希分片，同一用户的所有订单全部存入同一张分表，用户查询自己的订单时路由到单张分表性能极高；全局使用雪花算法生成分布式唯一主键保证主键不重复。

目前实训项目中没有落地 Sharding-JDBC，但是小组已经对齐了完整的分片扩展规范，后续有需求可以快速落地。

## 8、雪花算法时钟回拨问题

问：你们项目的分布式全局唯一 ID 用雪花算法，怎么解决服务器时钟回拨导致生成重复 ID 的问题？

答：我们对原生雪花算法做了优化，每次生成 ID 的时候校验当前系统时间和上次生成 ID 的时间，如果出现时钟回拨，回拨时间小于 50ms 就直接等待时间追上再继续生成，回拨时间大于 50ms 就抛出异常告警，或自动切换到备用 ID 生成服务，完全不会生成重复的订单 ID，避免后续支付、物流链路出现严重的业务异常。

## 9、批量导入性能优化

问：你们项目里批量导入 10 万条商品数据的时候，为什么会出现导入特别慢的问题，团队是怎么优化的？

答：最开始循环单条插入，逐条提交事务，频繁 IO 导致 10 万条商品导入要 2 分钟。

我们做了两点优化：一是关闭自动提交，每 1000 条批量事务提交，代码用 MyBatis 批量插入代替循环单存；二是导入前临时关闭索引，导入完成再重建。优化后耗时降到 10 秒内，同时这套方案定为团队批量数据处理统一规范。

【追加】如果数据量达到百万级，单纯批量事务依然会有锁表风险，可以通过 RocketMQ 分片异步导入，避免长事务锁表影响线上读写；大批量数据同步也可以使用 MySQL LOAD DATA 本地文件导入，是数据库原生最快方案。

## 流程图文字推演

### 雪花算法时钟回拨处理流程

生成 ID 请求 --> 获取当前系统时间 --> 与上次生成 ID 时间比较 --> 若时间正常，生成 ID --> 若发生时钟回拨，判断回拨时间是否小于 50ms --> 小于则等待时间追上再生成 --> 大于则抛出异常告警或切换备用 ID 生成服务

### 批量导入优化流程

原始方案：循环单条插入 --> 逐条提交事务 --> 频繁 IO，耗时 2 分钟

优化方案：关闭自动提交 --> 每 1000 条批量事务提交 --> 使用 MyBatis 批量插入 --> 导入前临时关闭索引 --> 导入完成后重建索引 --> 耗时降至 10 秒内

💡 **速记**

【核心考点】

SPU 与 SKU 拆分避免数据冗余和锁竞争，生产环境禁用物理外键，统一建表规范（逻辑删除、时间字段、下划线命名、utf8mb4）。

联合索引遵循最左前缀原则，避免索引失效（运算、前模糊、or、隐式转换等），定期 explain 和清理冗余索引。

InnoDB 使用 B+树，聚集索引存完整数据，二级索引存主键需回表，覆盖索引避免回表。

深分页使用主键游标分页，禁止大偏移量。

InnoDB 默认 RR 隔离级别，秒杀场景需加锁避免幻读和超卖。

分库分表按 user_id 哈希，雪花算法生成全局 ID，通过等待或切换备用服务解决时钟回拨。

批量导入优化：关闭自动提交、批量提交、临时关闭索引，百万级可结合 MQ 异步导入或 LOAD DATA。

【高频逻辑链】

索引设计：分析高频查询字段 --> 设计联合索引 --> 遵循最左前缀 --> 使用 explain 验证 --> 定期清理。

批量导入优化：关闭自动提交 --> 批量提交 --> 关闭索引 --> 导入后重建索引。

【关键避坑】

物理外键在批量操作时触发表锁，高并发场景应禁用，改由业务代码校验。

雪花算法时钟回拨必须处理，否则可能生成重复 ID，影响支付、物流等核心链路。

深分页 limit 大偏移量会导致全表扫描，必须改用游标分页。
