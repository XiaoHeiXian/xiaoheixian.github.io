## 1、秒杀库存超卖的成因与落地方案

问：秒杀库存超卖的成因是什么？你当时对比了哪三套落地方案，团队最终的落地流程是怎样的？

答：高并发场景下多个事务同时读取库存产生幻读，多线程同时执行扣减操作就会出现超卖。

我当时对比了悲观锁并发阻塞、乐观锁高并发下单失败多、Redis 预库存+分布式锁+MQ 异步三套方案，最终选定第三套落地。

我们 4 人分工，测试同学压测复现 bug，集体研讨选型，我实现核心锁逻辑，Elastic-Job 每日定时校对库存，彻底解决了超卖问题。

## 2、原生 SETNX 分布式锁的缺陷与 Redisson 解决方案

问：原生 SETNX 分布式锁有哪些缺陷？Redisson 是怎么解决可重入、看门狗自动续期、防止锁误删这些问题的？

答：原生 SETNX 锁不可重入、没有自动续期机制、不同线程容易误删其他线程的锁，服务宕机还会出现死锁问题。

Redisson 采用 Hash 结构存储线程计数实现可重入，默认过期时间防死锁，看门狗后台线程自动续期锁过期时间。

Redisson 由于内置了 UUID 校验的 Lua 脚本，在正常调用 unlock() 时，几乎不可能发生“误删其他线程锁”的情况。即使锁已过期被他人获取，unlock() 中的 hexists 校验也会失败，从而阻止删除操作。

## 3、缓存穿透、击穿、雪崩的成因与布隆过滤器落地

问：缓存穿透/击穿/雪崩三类问题的成因是什么？你们布隆过滤器是怎么落地的？

答：缓存穿透是大量非法无效 ID 请求直接打到 MySQL，我们用布隆过滤器拦截无效 ID+缓存空值解决。

缓存击穿是热点商品过期，大量并发请求瞬间打到数据库，我们用热点商品永不过期，更新加互斥锁解决。

缓存雪崩是大量 key 同时过期，数据库压力瞬间打满，我们用过期时间随机打散解决。

布隆过滤器封装进 common 公共模块，所有服务全局复用，从架构层面统一防护。

## 4、支付回调重复推送的接口幂等实现

问：支付回调重复推送，你们是怎么实现接口幂等的？

答：我们以支付流水号作为唯一 key，加 Redis 分布式锁，先查询订单支付状态，未支付再执行业务。

核心逻辑投递 MQ 异步消费，完全避免平台重复推送造成资损问题，保证重复调用永远不会重复更新订单状态。

## 5、30 分钟未支付自动关单的双兜底方案

问：30 分钟未支付自动关单，你们为什么用 RocketMQ 延时队列 + Elastic-Job 双兜底方案？

答：单机 @Scheduled 定时任务多实例部署会重复执行。

主方案用 RocketMQ 延时队列保证关单时效性，兜底采用 Elastic-Job 分布式定时任务，限制单实例执行，每日巡检超时订单。

两个人分工开发两套定时组件，双重兜底确保不会出现漏单的问题。

## 6、为什么选择 Elasticsearch 做商品搜索

问：你在微云商城项目中，为什么选择 Elasticsearch 来做商品搜索，而不是直接用 MySQL？

答：我们当时选型的核心依据是商品搜索的三大核心诉求：全文检索、多维度筛选、毫秒级高并发查询，ES 对比 MySQL 有不可替代的优势。

第一是倒排索引的检索速度完全碾压 MySQL，MySQL 用 LIKE %关键词% 做模糊查询会直接触发全表扫描，索引完全失效，商品量过十万之后查询耗时直接涨到秒级；ES 基于倒排索引设计，检索速度是 MySQL 的 10 到 100 倍，还支持集群水平扩容，百万级商品数据就能做到毫秒级检索，同时它内置了中文分词、同义词、模糊匹配、搜索结果高亮的能力，完美适配商品名称、详情的模糊搜索场景。

第二是它的近实时索引同步能力，完全满足电商的实时性要求，商品上下架、价格修改之后，数据能快速同步到检索库，用户能实时看到最新的商品信息，完全适配电商的实时运营需求。

## 7、MySQL 商品数据同步到 Elasticsearch 的方案

问：那你们项目里是怎么把 MySQL 的商品数据同步到 Elasticsearch 的？

答：我们用的是全量初始化+Binlog 增量异步同步的架构，完整链路是 MySQL -> Canal -> RocketMQ -> Elasticsearch。

首次全量同步的时候，项目刚启动或者新商品库接入，我们会分页读取 MySQL 全量商品数据，做完字段清洗、补齐检索需要的扩展字段之后，批量写入 ES，完成基础数据初始化。

增量实时同步的链路里，我们先把 MySQL 的 binlog 日志模式设置为 row 行模式，完整记录商品表的增删改操作明细；然后用 Canal 客户端监听 MySQL 的 binlog，把日志解析成标准 JSON 消息发送到 RocketMQ 里；用 MQ 解耦 Canal 和 ES，既能削峰缓冲，又能避免商品大批量更新的时候 ES 写入压力过大；最后消费服务监听 MQ 的消息，做完数据清洗和字段补全，根据操作类型执行 ES 的新增、更新、删除文档操作，整个链路没有强侵入性，同步延迟控制在 2 秒以内，完全满足电商实时性要求。

## 8、Elastic-Job 任务执行超 24 小时的解决方案

问：你们项目里用 Elastic-Job 做分布式定时任务，有没有遇到过任务单次执行超过 24 小时的情况？是怎么解决的？

答：我们没有遇到过这种情况，可能是我们的全量同步数据量不够，如果遇到了任务执行超过 24 小时的问题，会造成任务积压、资源长期占用，还会错过定时调度。

我们已经做了预案，解决思路是从任务拆分、资源扩容两个维度落地。

首先是根本优化，拆分任务降低单次执行的负载：第一细化任务分片，按照商品 ID 哈希做分片，增加任务分片总数，多台服务节点并行处理，直接缩短单次执行耗时；第二集群资源扩容，临时扩容 Elastic-Job 的执行节点，让更多节点分担分片任务，同时扩容数据库和 Redis 的资源，消除底层存储的性能瓶颈，加快任务处理速度。

## 9、支付结果主动回查的原因与实现

问：电商支付场景里，为什么要做支付结果主动回查？你们的支付宝支付回查是怎么实现的？

答：核心原因是支付宝的异步通知本身不可靠，主动调用支付宝官方查询接口做结果兜底，才能保证本地订单状态和支付宝真实交易状态完全一致，解决四类异常场景：

第一是异步通知丢失，服务器防火墙、网络波动、应用服务重启都可能导致回调通知接收失败，后台没法自动感知支付成功，订单会一直停留在未支付状态；

第二是前端页面中断，用户付完钱直接关页面、网络中断，前端没法同步最新状态，用户页面还显示支付中，但支付宝那边交易实际已经成功了；

第三是防止恶意伪造支付成功通知，攻击者伪造回调请求篡改本地订单状态，主动调用支付宝官方接口校验真实交易状态，从源头避免伪造请求导致的资金损失；

第四是覆盖边缘异常场景，支付超时关闭、支付后全额退款、回调重复推送这些边界场景，只靠异步通知根本处理不全，主动回查做全局状态确认兜底。

我们的支付宝回查是基于 Java 技术栈落地的完整方案：

用户下单生成订单之后，先向 RocketMQ 投递一条 5 分钟的延时消息，给异步通知预留足够的接收时间，避免刚下单就回查造成无效调用；

消费端收到回查消息之后，先校验本地订单状态，如果订单已经是已支付状态，直接结束本次任务，不用做多余回查；

如果订单还是未支付或者支付中，就去查询本地的支付流水记录表，如果已经存在该订单的成功支付流水，直接更新订单状态为已支付就结束流程；

没有本地支付流水的话，再调用支付宝官方的（alipay.trade.query）接口，传入商户订单号查询真实交易状态，如果返回 TRADE_SUCCESS 或者 TRADE_FINISHED，就新增本地支付流水记录，更新订单状态为已支付，执行后续的发货、积分发放逻辑；如果返回未付款或者交易关闭，就不修改订单状态，等待后续定时任务再次回查。

最后我们还做了全局兜底，除了延时消息之外，新增一个定时任务，每日轮询创建超过 30 分钟还未支付的订单，批量调用支付宝接口回查状态，彻底覆盖延时消息丢失、消费失败的极端场景，同时更新订单状态的时候，我们会携带订单号作为幂等标识，避免重复回查多次更新订单、重复执行发货逻辑。

## 流程图文字推演

### 秒杀超卖解决方案流程

用户请求秒杀 --> Redis 预减库存（Lua 脚本保证原子性） --> 库存不足直接返回 --> 库存充足则发送 MQ 异步消息 --> 消费者监听消息，执行数据库扣减 --> 分布式锁保证并发安全 --> Elastic-Job 定时校对库存

### 支付回调幂等流程

支付平台回调 --> 以支付流水号为唯一 Key 加 Redis 分布式锁 --> 查询本地订单支付状态 --> 若已支付则直接返回 --> 未支付则执行业务逻辑（更新订单状态） --> 投递 MQ 异步处理后续发货、积分等

### 数据同步流程

MySQL 开启 binlog（row 模式） --> Canal 监听 binlog --> 解析为 JSON 消息 --> 投递 RocketMQ --> 消费者监听消息 --> 数据清洗与字段补全 --> 根据操作类型调用 ES 接口（新增/更新/删除）

### 支付回查流程

用户下单生成订单 --> 投递 5 分钟延时消息到 RocketMQ --> 消费端收到回查消息 --> 校验本地订单状态：若已支付则结束；若未支付则查询本地支付流水 --> 有成功流水则更新订单状态；无流水则调用支付宝 alipay.trade.query 接口 --> 返回 TRADE_SUCCESS/TRADE_FINISHED 则新增流水、更新订单状态；否则不修改 --> 每日定时任务批量回查超时未支付订单做全局兜底

💡 **速记**

【核心考点】

秒杀超卖：Redis 预库存 + 分布式锁 + MQ 异步 + Elastic-Job 校对。

Redisson 解决 SETNX 缺陷：Hash 可重入、看门狗续期、Lua 脚本防误删。

缓存三兄弟：穿透用布隆过滤器 + 空值缓存；击穿用热点永不过期 + 互斥锁；雪崩用过期时间随机打散。

支付回调幂等：支付流水号唯一 Key + Redis 分布式锁 + 先查后处理 + MQ 异步。

自动关单：RocketMQ 延时队列保时效 + Elastic-Job 分布式定时兜底。

ES 选型：倒排索引碾压 MySQL LIKE，毫秒级、高并发、全文检索。

数据同步：全量初始化 + Binlog 增量，链路 MySQL -> Canal -> RocketMQ -> ES。

定时任务超时：任务分片（商品 ID 哈希）+ 集群扩容 + 存储扩容。

支付回查：延时消息 + 定时任务双保险，主动调用支付宝接口，幂等更新订单。
