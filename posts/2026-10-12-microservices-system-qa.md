## 1、Maven 多模块分层设计与循环依赖规避

问：你们项目 Maven 多模块分层结构是怎么设计的？团队是怎么规避循环依赖、代码冲突这类问题的？

答：父工程统一管控所有依赖版本，拆分 common 公共工具模块、api 统一存放所有 Feign 接口与 DTO 实体，各个业务微服务完全独立拆分。

团队采用 Git 功能分支 + CodeReview 机制，严格规定仅允许在 api 层做远程调用，所有长链路同步调用全部改成 RocketMQ 异步化，从架构层面杜绝服务强耦合、循环依赖的问题。

## 2、OpenFeign 底层原理与 Sentinel 三层防护

问：OpenFeign 底层原理是什么？什么是服务雪崩？你们项目里 Sentinel 三层防护是怎么落地的？

答：OpenFeign 基于 JDK 动态代理封装 HTTP 请求，同步链式调用如果下游服务故障很容易引发服务雪崩。

我在项目里主导接入 Sentinel，完整实现限流、熔断、降级三层防护：配置限流保护核心接口，服务异常率或慢调用比例达到阈值自动熔断，返回预设兜底结果，通过并发压测验证整套防护效果。

## 3、Nacos 优势与防止配置混乱

问：Nacos 优势是什么？你们团队是怎么防止多人并行开发搞乱配置的？

答：Nacos 同时集成注册 + 分布式配置中心，天然支持灰度发布、长连接推送配置变更。

我们项目里数据库连接信息、密钥、参数等配置全部统一存放在 Nacos 配置中心，严格区分开发、测试、生产多环境命名空间，完全禁止本地硬编码配置，避免多人开发互相覆盖配置。

## 4、OpenFeign 调用超时问题解决

问：你们用 OpenFeign 调用下游服务的时候出现了 ReadTimeout 超时，解决这个问题的？

答：配置 Feign 的超时时间远大于业务的平均响应时间，搭配 Sentinel 的超时熔断机制，下游服务连续超时自动返回兜底降级结果，不会一直阻塞等待拖垮整个调用链。

## 5、Nacos 宕机后微服务启动与单点故障避免

问：Nacos 配置中心如果宕机了，你们项目的微服务还能正常启动运行吗？怎么避免配置中心单点故障问题？

答：微服务本地会缓存一份上次拉取到的配置快照，就算 Nacos 宕机，本地有缓存的前提下服务完全可以正常启动运行；第一次启动没有缓存的场景下，服务会失败重试拉取配置，不会直接退出。

生产环境我们后续会搭建 Nacos 三节点集群，搭配 MySQL 共享存储实现高可用，完全避免配置中心单点故障。

## 6、网关层统一鉴权的原因

问：你们网关层全局统一鉴权，为什么不把鉴权逻辑放到每个业务服务里面实现？

答：如果每个微服务都单独写一遍 JWT 鉴权逻辑，会出现大量重复代码，而且后续要升级鉴权规则的时候，需要发布所有服务，维护成本极高。

我们把鉴权逻辑统一放在网关层实现，所有请求进入业务服务之前就完成身份校验，直接过滤掉非法请求，还能统一在这里做请求日志埋点、跨域处理、参数校验，业务服务完全不用关心鉴权相关的逻辑，只需要专注处理自身业务即可。

## 7、循环依赖的解决方案与异步解耦选型

问：微服务之间调用出现循环依赖的时候，除了改成 MQ 异步解耦，还有其他什么落地方案？你们团队为什么最终选择异步解耦？

答：理论上可以通过拆分中间公共服务的方式，把两个服务互相调用的公共逻辑抽离成独立的公共服务，两个业务服务都调用公共服务，避免直接互相依赖。

但是我们电商项目里删除购物车、发送通知这类非核心链路的操作，根本没必要做同步强依赖，改成异步 MQ 解耦之后，主流程的响应速度大幅提升，就算下游服务短暂故障，消息还可以持久化不会丢失，可用性比同步调用高得多，所以团队最终选了异步解耦的方案。

## 8、微服务架构选型与拆分粒度把控

问：你在项目中为什么选择微服务架构？服务拆分时是如何把控拆分粒度的？

答：我们最初用单体架构快速搭原型，但很快遇到三个痛点：一是业务模块耦合严重，修改一个功能要牵动整个系统；二是团队协作效率低，4 人团队在同一个代码库上工作，合并冲突频繁；三是流量波动大，无法按需扩展。

当然，我们也清楚微服务会带来分布式事务、服务治理等新挑战，所以最终选择了 SpringCloud Alibaba 微服务架构。落地后收益很明显：业务完全解耦，各服务独立部署、独立测试，迭代互不干扰；通过 Sentinel 熔断隔离故障，提升系统可用性；不同服务可按需选型，订单用 MySQL 保障事务、搜索用 ES 实现毫秒级检索，不受统一技术栈限制；4 人按服务分工并行开发，Git 冲突归零。

拆分粒度上我们没有盲目追求越细越好，全程以高内聚低耦合为核心标尺，严格按 DDD 业务域拆出商品、订单、用户、支付、搜索 5 个独立微服务，每个服务只负责单一业务域能力，绝不跨域实现逻辑，防止跨服务调用链路过长、运维成本暴涨，比如最初把搜索逻辑放在商品服务里，后来发现搜索迭代频繁，每次改完都要重启商品服务，容易影响核心链路稳定性，于是把搜索独立成 ES+RAG 专属检索服务，性能和可维护性达到了最优平衡。

## 流程图文字推演

### 微服务架构选型与拆分流程

单体架构原型 --> 遇到痛点（耦合严重、协作效率低、无法按需扩展） --> 评估微服务挑战（分布式事务、服务治理） --> 选择 SpringCloud Alibaba --> 按 DDD 业务域拆分（商品、订单、用户、支付、搜索） --> 独立部署与按需选型 --> 迭代优化（搜索独立为 ES+RAG 服务）

### Sentinel 三层防护流程

请求进入 --> 限流保护核心接口 --> 检查服务异常率或慢调用比例 --> 达到阈值触发熔断 --> 返回预设兜底结果

💡 **速记**

【核心考点】

Maven 多模块分层：父工程统一管控依赖，common 公共模块，api 层存放 Feign 接口与 DTO，业务服务独立拆分。

循环依赖规避：禁止在业务层直接跨服务调用，长链路同步调用全部改为 RocketMQ 异步化，使用 Git 分支 + CodeReview 规范。

OpenFeign 原理：基于 JDK 动态代理封装 HTTP 请求，同步链式调用易引发服务雪崩，需搭配 Sentinel 实现限流、熔断、降级。

Nacos 优势：集成注册与配置中心，支持灰度发布与长连接推送，通过多环境命名空间隔离配置，生产环境三节点集群 + MySQL 共享存储避免单点故障。

网关统一鉴权：将 JWT 校验、日志埋点、跨域处理、参数校验统一放在网关层，避免业务服务重复开发。

微服务拆分粒度：以高内聚低耦合为核心标尺，按 DDD 业务域拆分为商品、订单、用户、支付、搜索 5 个独立微服务。

【高频逻辑链】

微服务选型：单体痛点（耦合、协作、扩展） --> 评估微服务挑战 --> 选择 SpringCloud Alibaba --> DDD 拆分 --> 独立部署与按需选型 --> 迭代优化。

Nacos 容灾：本地缓存配置快照 --> 宕机时服务仍可启动 --> 首次启动失败重试 --> 生产环境三节点集群 + MySQL 共享存储。

【关键避坑】

Nacos 宕机时，第一次启动没有缓存的场景下，服务会失败重试拉取配置，不会直接退出，但需要确保本地缓存机制生效。

微服务拆分粒度不是越细越好，要防止跨服务调用链路过长、运维成本暴涨，需以高内聚低耦合为核心标尺，按 DDD 业务域拆分。
