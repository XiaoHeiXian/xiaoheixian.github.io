## 1、为什么在商城引入 RAG 商品智能搜索

问：什么是 RAG？商城已经有 ES 搜索，为什么还要增加 AI 智能搜索？

答：RAG 是检索增强生成，简单说就是先从知识库检索相关资料，再让大模型结合检索结果生成回答。这样模型回答时可以参考商品数据，而不是完全依赖自身已有知识。

商城的 ES 搜索适合关键词检索，以及分类、品牌、价格等结构化筛选；AI 智能搜索主要处理比较口语化、模糊的需求，例如“预算 4000 元，想买一部续航好的手机”。系统可以把用户需求和商品描述转成向量，找出语义相关的商品，再整理推荐理由。

两者侧重点不同：ES 更便于处理明确的关键词和筛选条件，RAG 有助于理解自然语言，但语义相近不代表一定满足价格、库存等硬条件，这些仍需结构化过滤或业务校验。

## 2、ES 与 AI 搜索如何配合

问：你们的 ES 与 RAG 双引擎是怎么配合的？两边的结果会合并排序吗？

答：按照商城博客中的方案，用户输入自然语言后，前端发起两类请求：一类获取 AI 推荐，另一类提取搜索条件。条件提取会把用户的话转换成关键词、最低价和最高价，再用于 ES 商品查询；AI 推荐则结合向量检索结果生成商品列表和推荐理由。

例如用户搜索“2000 到 4000 元的小米手机”，条件提取可以得到关键词和价格区间，用于 ES 搜索；推荐路径可以结合商品资料给出推荐。博客中的设计是分别展示商品列表和“为你推荐”，没有展示将两路结果合并重排的实现。

前端示例使用 Promise.allSettled 并发发起请求，但它会等两项请求都结束后再统一处理结果。一路超时或失败时如何展示，需要结合实际的超时和降级代码验证。

## 3、商品数据如何构建向量知识库

问：商城商品数据是怎么从 MySQL 进入向量库的？

答：博客中的同步流程是先从 MySQL 的 sku_info 表读取未删除的商品，再把每条商品记录转换为 Document。Document 可以理解成一条供检索的文档，包含用于检索的文本内容和附加信息。

商品名称、规格、品牌、分类和价格会被拼成文本；SKU ID、图片地址等字段保存在 metadata，也就是元数据中。之后对文本进行分块，用 Embedding 模型把文本转换成向量，最后分批写入 Redis 向量库。用户搜索时，系统也将查询文本转换为向量，再查找语义相近的商品资料。

例如一条手机 SKU 的名称和规格用于语义检索，图片地址用于结果展示。博客展示的是文本向量化，没有展示对图片本身生成向量，也不能据此说已经实现以图搜图。

## 4、文本分块怎么做

问：商品数据为什么要分块？你使用了什么分块策略？

答：分块是把较长文本拆成便于检索的小片段，避免把整篇说明都交给模型，也方便只召回和用户问题有关的内容。比如商品说明中包含屏幕、续航和拍照介绍，检索续航问题时可以优先找相关片段。

博客示例使用 RecursiveCharacterTextSplitter，按照段落、换行、句号、逗号等分隔符逐级尝试切分，配置 chunk_size=256、chunk_overlap=25，并使用指定的 tiktoken 编码估算 Token 数。相邻片段保留一定重叠，是为了减少信息在切分边界被截断的问题。

这里是固定参数的递归分块，不等于根据商品类型自动调整参数的动态分块。短商品文本也可能自然保持为一块；参数是否合适，应通过实际查询样本评估召回效果和成本。

## 5、向量数据如何更新

问：商品向量重复同步怎么办？商品修改或下架后，向量库如何保持一致？

答：博客示例使用 SKU ID 和分块内容生成 MD5 文档 ID。同一个商品的相同片段再次同步时，使用相同 ID，有助于避免生成不同 ID 的重复文档。

但商品内容发生变化时，新的内容可能生成新的 ID，旧片段不会因为生成了新 ID 就自动删除。例如商品名称改变后，向量库里可能同时留有新旧描述。因此，完整同步方案还需要考虑如何根据 SKU 查找并清理旧片段、同步下架和删除状态，以及失败重试和对账。

当前博客主要展示全量读取和写入示例，不能仅凭 MD5 就说已经完整解决增量同步和数据一致性。即使向量数据更新了，下单前仍应查询业务系统确认最新价格、状态和库存。

## 6、如何降低商品推荐中的幻觉

问：大模型可能编造商品信息，商城是怎么控制的？

答：博客方案首先通过向量检索提供商品上下文，再在提示词中要求模型只根据检索到的信息推荐商品；没有匹配内容时返回空商品列表，并使用结构化 Schema 约束返回格式。

例如用户要找某种手机，但知识库没有相关商品时，系统应返回“暂无相关信息”，而不是编造商品。结构化输出让 Java 和前端更容易解析商品列表、总结和推荐理由，但 JSON 格式正确不代表商品事实一定正确。

因此，还可以进一步做候选 SKU 校验，以及价格、上下架状态等业务数据核验；这些属于需要额外实现和验证的增强措施。博客展示的提示词和 Schema 约束不能直接等同于完整的三层幻觉拦截，也没有足够证据支持具体的幻觉率下降数字。

## 7、SpringCloud 如何集成 Python AI 服务

问：商城是 Java 微服务，为什么 AI 服务用 Python？两边怎么调用？

答：博客方案由 Python FastAPI 承载 LangChain 和商品向量检索能力，Java 智能搜索服务负责与现有 SpringCloud 业务系统对接。调用链路是前端经过 Gateway 到 Java 服务，Java Service 再通过 OpenFeign 发送 HTTP 请求给 Python，收到结果后转换成 Java DTO 返回前端。

例如 Python 推荐接口返回 summary、product_list 和 reason，Java 检查返回码，并将下划线命名字段映射为 Java 属性，最后交给前端展示。博客中的 Python 侧使用 LangChain；简历中如果提到 LangChain4j，需要按自己对 Java 框架的实际掌握情况说明，不能把两者当成同一个实现。

Python 服务的地址也要根据部署环境配置：博客中的 127.0.0.1 适合特定同机运行方式，Java 和 Python 分别部署在不同容器时，需要使用容器之间可访问的地址。

## 8、AI 搜索如何处理会话、超时和降级

问：多轮搜索如何记住上下文？AI 服务太慢或者不可用怎么办？

答：博客方案通过 threadId 区分会话，保存对话上下文。例如用户先问“4000 元以内的手机”，接着问“有没有续航更好的”，系统可以结合前一次的预算理解后续问题。会话能否跨重启保留、是否与用户身份安全绑定，取决于实际存储和鉴权实现。

Java 调用 Python 时需要分别考虑连接超时和读取超时。超时时间应结合用户体验、线程与连接资源设置；博客里的六分钟只是示例，不能直接作为线上推荐值。客户端等待超时也不代表 Python 端的任务一定停止。

AI 推荐不可用时，可以设计为提示用户推荐暂不可用，并尝试保留普通 ES 搜索。但条件提取本身也可能依赖 AI，因此应明确回退规则，例如让用户使用原始关键词搜索。降级是否生效，需要通过实际代码和故障测试确认。

## 流程图文字推演

### 商品向量同步流程

MySQL 商品数据 --> 转换为 Document --> 拼接商品文本并保留 SKU 元数据 --> 按固定参数分块 --> Embedding 生成向量 --> 分批写入 Redis 向量库。

### 智能搜索流程

用户输入自然语言 --> 一路提取关键词与价格条件并查询 ES --> 另一路检索商品向量并生成推荐理由 --> 前端分别展示商品搜索结果与 AI 推荐。

### SpringCloud 集成流程

前端 --> Gateway --> Java 智能搜索服务 --> OpenFeign --> Python FastAPI AI 服务 --> 返回 JSON --> Java 转换 DTO --> 前端展示。

## 💡 **速记**

【核心考点】

- RAG 是先检索资料，再结合资料生成回答；它不能保证事实一定正确。
- ES 负责关键词和结构化筛选，AI 侧重语义召回与推荐解释；博客中两路结果分别展示。
- 商品文本来自名称、规格、品牌、分类和价格；SKU ID、图片等作为元数据。
- 博客展示固定参数递归分块，chunk_size=256、chunk_overlap=25，不等于自适应动态分块。
- 内容 MD5 有助于相同片段去重，但不能自动清理修改后的旧向量。
- 提示词、空结果和 Schema 约束可以降低风险，但不等于完整三层幻觉拦截。
- Java 通过 OpenFeign 调用 Python AI 服务，需要关注服务地址、超时、返回校验与降级。

【关键避坑】

- 不把博客里的设计设想说成已经实现或上线的能力。
- 语义相似度不能替代价格范围、商品状态和库存校验。
- JSON 格式正确不代表商品信息真实；没有评测记录时不编造召回率或幻觉率提升数字。
- Python LangChain 与 Java LangChain4j 是不同生态的框架，结合实际经验说明。
